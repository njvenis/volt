# G7 backup and recovery v1 contract — draft for review

Status: **draft; independent review required before structural implementation**. This contract is a local development target for FR-OP-01, G7-REC-01 and G7-PKG-01. It chooses no production schedule, retention/deletion policy, credentials, RPO, RTO, archive location or recovery profile. Fixture values and local Docker evidence do not establish a production policy or gate result.

## Authority and boundary

UVM is the immutable desired-settings, authorization, audit and command-receipt authority. It commits a new desired revision, audit event, command receipt and host intent atomically. A receipt proves only that the desired revision committed. UVM has no Docker, volume, archive, signing-key or general host command authority, and never writes DefectDojo tables.

An independently operated host controller owns the deployment registry, settings validation bounds, archive-target and recovery-profile registries, schedule, controller journal, signing keys, archive access, runtime fencing and monotonically increasing recovery epoch. Refs crossing the API are opaque registry identifiers; they are not paths, URLs, credentials or executable instructions. Host credentials and registry contents never enter UVM settings, audit, receipts or public responses. The controller uses a dedicated deployment-bound identity with only desired-settings read, signed report/acknowledgement/recovery-event submission, and mutual-TLS sequence resynchronization authority.

Add exact-deployment grants `backup.settings.read` and `backup.settings.configure`. A grant must include the deployment ID in the same complete grant as the action; explicit denies take precedence. No observer grant or bootstrap-admin status implies either action. Enforce current server-side grants on every public read and write, and controller identity, signature and deployment binding on host routes. Preserve session and CSRF checks for browser writes. Authorization failure must not disclose whether another deployment or command exists.

## Public v1 API and DTOs

Public product routes are under `/api/v1/operations/backup-settings/{deployment_id}` and are served by the UVM product listener. Recovery-control routes use a separate, deployment-bound listener and the `/recovery-control/v1/{deployment_id}/...` prefix; they are never mounted on the verification-only product listener. Every request and response has `schema_version: 1`; reject unknown write members, booleans where integers are required, missing members and unsupported versions. Revision counters and epochs are non-negative JSON integers (never booleans); IDs are UUIDs except deployment/registry refs and stable actor IDs; timestamps are UTC RFC 3339 strings; digests are `sha256:<64 lowercase hex>`. Optional members are present as `null`.

| Method and path | Grant / identity | Behaviour |
|---|---|---|
| `GET /api/v1/operations/backup-settings` | authenticated principal; deployment-specific read grants | Page the trusted deployment registry with fixed page size 50. Resolve current read grants before counting or paging; return no entries for deployments without the grant. |
| `GET /` | `backup.settings.read` | Public sanitized desired/effective/status readback and current revision tokens. |
| `GET /revisions/{revision}` | `backup.settings.read` | Immutable historical settings and publication provenance. |
| `POST /commands` | `backup.settings.configure` | Publish a complete settings document or rollback by copying a retained revision into a new revision; automatic host application intent. |
| `GET /receipts/{command_id}` | read grant plus same actor or explicit audit-view authority | Non-disclosing command receipt lookup. |
| `GET /recovery-control/v1/{deployment_id}/desired` | deployment-bound controller over mutual TLS | Complete desired values and policy/authority/configuration tokens. |
| `POST /recovery-control/v1/{deployment_id}/reports` | deployment-bound controller plus valid host signature | Admit an idempotent signed status report after sequence/epoch checks. |
| `POST /recovery-control/v1/{deployment_id}/acks` | deployment-bound controller plus valid host signature | Admit application acknowledgement with requested and active revision/digest. |
| `POST /recovery-control/v1/{deployment_id}/recovery-events` | deployment-bound controller plus valid host signature | Admit signed restore epoch and recovery result; replay-safe. |
| `POST /recovery-control/v1/{deployment_id}/sequence-resync` | deployment-bound controller over mutual TLS | Reconcile a rolled-back UVM sequence cursor to the external control-plane checkpoint; retain exact acknowledgement in host journal. |
| `POST /recovery-control/v1/{deployment_id}/connector-quarantine` | deployment-bound controller plus valid host signature | Place named connector intents into a durable non-dispatchable quarantine for this recovery UUID/epoch. This route cannot release or dispatch intents. |

The recovery-control listener is a separate socket with mutual TLS, a controller-certificate-to-deployment allowlist and host-network ACL permitting only the independent host controller. Host client credentials, signing keys and the authoritative controller journal remain outside the container. The external host controller obtains the epoch/sequence checkpoint, performs mutual-TLS resynchronization, journals the exact acknowledgement and submits signed connector-quarantine requests. The in-container recovery-control process only validates and durably records those narrow submissions, serves the deployment-bound desired read, and gates verification startup; it does not obtain external credentials, sign as the host, or own the authoritative host journal. It has no general UVM route table. The product listener, while in recovery verification mode, serves only allowlisted GET/HEAD health/readback routes. Recovery proceeds in this order: external host obtains checkpoint; start the restricted recovery-control listener only; external host performs resync and submits connector quarantines, which the in-container listener validates/persists; then start the verification-only UVM and CE product listeners. No general product write, webhook, polling, task dispatch, or automatic migration runs in this sequence. A required schema migration is a separately authorized one-shot offline migration process after pre-migration readback, while ingress/egress and dispatch remain fenced; verification-only listeners are restarted afterward. It is not an API write route and cannot release the recovery fence.

### Backup deployment discovery

`GET /api/v1/operations/backup-settings` accepts only an optional opaque
`cursor` query parameter and always uses a fixed page size of 50. The server
loads deployment identities and labels only from its trusted deployment
registry. Under the existing global policy lock it resolves the current
principal's native authority and explicit denies, then filters the registry by
the exact `backup.settings.read` grant before calculating page totals or
selecting a page. `can_configure` is independently computed from the exact
deployment `backup.settings.configure` grant. Registry membership, labels and
other deployment existence are never used to answer a direct lookup for a
deployment the actor cannot read; direct settings, revision and receipt routes
return the same non-disclosing not-found response for absent and unauthorized
deployments.

Sort both registry and authorized projection by bytewise ascending
`deployment_id` before hashing, counting or paging. The authenticated opaque
cursor binds the stable actor ID, current global `policy` revision, current
native `authority` revision, SHA-256 digest of the complete trusted registry
(every ordered deployment ID, sanitized label, host principal ID and
verification-key digest), SHA-256 digest of the complete currently authorized
projection (every ordered `deployment_id`, sanitized `label`, and evaluated
`can_configure` value under the current request authority), and the next
offset. On every continuation request, recompute both complete digests and the
projection under the current request authority before returning any page.
Reject an expired, malformed or context-changed cursor with HTTP 409 and a generic
`revision_conflict` response; do not return counts, labels or deployment IDs
from its former context. A new first-page request after any actor, policy,
authority, registry or authorization-projection change is required.

The exact success response is:

```json
{"schema_version":1,"deployments":[{"deployment_id":"g7-local","label":"Local development","can_configure":true}],"next_cursor":null}
```

`deployments` contains at most 50 objects, each with exactly `deployment_id`,
`label`, and `can_configure`. `deployment_id` is the opaque trusted-registry
key, `label` is the sanitized registry label, and `can_configure` is a JSON
boolean. `next_cursor` is either null or an opaque string; its contents and
page offset are never exposed separately. An empty authorized result returns
the same shape with an empty list and null cursor.

Example numbers and refs above are format illustrations only, not host policy. Before the first corresponding record, `desired`, `effective`, `host_policy`, completed archive, application and restore verification are explicitly `null` or `unknown`. Initially `configuration`, unknown `host_policy` and `recovery_epoch` are zero; `policy` and `authority` expose their actual current global-policy and native-grant revisions and are never reset by this feature. `policy` is the existing global UVM policy revision; `authority` is the native permission/grant revision; `host_policy` is the independent controller-policy revision. These are separate tokens and all appear in every current readback, command precondition, receipt, and host desired readback. Deployment and registry refs are opaque stable strings; actor IDs are stable identity strings, never assumed to be UUIDs; command, audit, intent, report, acknowledgement, event and controller-instance IDs are UUIDs. Application state is one of `pending`, `applied`, `failed`, `uncertain`, `unknown`; its object always identifies requested revision/digest, intent, host-policy revision, active revision/digest, report time and failure code (nullable where unavailable). `applied` requires exact equality of requested and active revision/digest and a valid authenticated acknowledgement. `completed_archive.outcome` is `complete`, `failed`, `uncertain` or `null`; only a verified complete manifest populates it. Freshness is `fresh`, `stale` or `unknown`, computed from signed archive `completed_at` against the `maximum_backup_age_seconds` in the verified effective settings revision, not desired settings, host bounds, settings application time or latest report time. With no verified effective revision, freshness is unknown. Restore verification is `verified`, `failed`, `uncertain` or `unknown`. These dimensions are independent: applied settings do not mean an archive completed, a completed archive can be stale, and neither proves restore verification.

The initial `GET /` shape is the same DTO with `desired:null`, `effective:null`, `status.settings_application:null`, `status.completed_archive` containing all-null members and `outcome:null`, freshness unknown with null evaluation, age, completion basis and maximum age, restore verification unknown with epoch zero and null archive/time/code, and `host_policy:null`; `configuration`, `host_policy` and `recovery_epoch` are zero, while `policy` and `authority` equal their actual current UVM revisions. `can_configure:false` until a fresh signed host policy exists. `GET /revisions/{revision}` returns exactly `{"schema_version":1,"deployment_id":"g7-local","revision":2,"digest":"sha256:<digest>","values":{<same six settings members>},"publication_revisions":{"configuration":2,"policy":5,"authority":7,"host_policy":3},"command_id":"<uuid>","actor_id":"<stable-id-string>","rationale":"<sanitized reason>","evidence_ref":null,"committed_at":"<UTC-time>","audit_id":"<uuid>"}`. Unknown revisions are non-disclosing 404s.

`GET /receipts/{command_id}` returns exactly `{"schema_version":1,"command_id":"<uuid>","deployment_id":"g7-local","actor_id":"<stable-id-string>","action":"backup.settings.publish|backup.settings.rollback","request_digest":"sha256:<digest>","settings_digest":"sha256:<digest>","desired_revision":3,"evaluated_revisions":{"configuration":2,"policy":5,"authority":7,"host_policy":3},"audit_id":"<uuid>","intent_id":"<uuid>","committed_at":"<UTC-time>","outcome":"desired_committed"}`. All fields are required; this endpoint cannot convert the commit receipt into an application claim.

`POST /commands` body is exactly one of:

```json
{"schema_version":1,"command_id":"<uuid>","action":"backup.settings.publish","expected_revisions":{"configuration":2,"policy":5,"authority":7,"host_policy":3},"rationale":"<non-secret reason>","evidence_ref":null,"values":{"interval_seconds":3600,"timeout_seconds":900,"maximum_backup_age_seconds":90000,"restore_verification_timeout_seconds":1800,"archive_target_ref":"archive-target-local-a","recovery_profile_ref":"recovery-profile-local-a"}}
```

or `action: "backup.settings.rollback"` with `rollback_revision` in place of `values`. Rollback always creates a new revision and is validated against the current host policy. `evidence_ref` is nullable and opaque. Success returns exactly the receipt DTO defined above, with all four evaluated revision tokens. It never claims host application.

There are separate integer tokens `configuration`, global UVM `policy`, native `authority` and external `host_policy`; none substitutes for another. Each command supplies all four expected tokens. Use one serializable UVM transaction and the existing lock order: global policy lock first, native deployment authority lock second, deployment settings lock third, and receipt/intent row locks or inserts last. Under the global policy lock evaluate the current policy revision; under the following authority lock evaluate current disclosure/configure authorization before disclosing or looking up a command ID. While retaining both locks, perform a non-locking receipt lookup: an exact same-actor/deployment canonical-request replay returns its receipt without rechecking old revision tokens; changed content conflicts. If no receipt exists, acquire the settings lock, compare all four expected tokens with the locked current values, and require a signed fresh external host-policy snapshot. Missing/stale host policy returns 503 `host_policy_unavailable`, `outcome:not_committed`. Under the same transaction and retained global policy, authority and settings locks, commit immutable revision, sanitized audit, receipt and intent atomically; any receipt/intent row lock or insert is last. This ensures existing policy and authorization writers serialize with backup publication and removes authorization/revision TOCTOU. Definite failure rolls all four writes back. Lost commit acknowledgement is `unknown` until exact receipt lookup. Do not let a later revision overtake an unresolved host intent. Errors use the existing versioned envelope and distinguish `not_committed` from `unknown`. Once a valid desired revision exists, later host outage does not stop the host's last-good schedule.

## Host DTOs, policy and signed report rules

`GET /recovery-control/v1/{deployment_id}/desired` returns exactly this nullable DTO (the route returns 200 with `desired:null` before first configuration):

```json
{"schema_version":1,"deployment_id":"g7-local","revisions":{"configuration":2,"policy":5,"authority":7,"host_policy":3},"desired":{"revision":2,"digest":"sha256:<64-lowercase-hex>","values":{"interval_seconds":3600,"timeout_seconds":900,"maximum_backup_age_seconds":90000,"restore_verification_timeout_seconds":1800,"archive_target_ref":"archive-target-local-a","recovery_profile_ref":"recovery-profile-local-a"},"command_id":"<uuid>","intent_id":"<uuid>","issued_at":"2026-10-27T12:00:00Z"}}
```

The host independently checks schema, digest, revision order, configured numeric bounds, registered opaque refs and its expected policy. Unknown, unregistered or revoked refs fail closed. The controller journals the intent before acting and retains last-known-good scheduling when settings are absent, invalid, rejected or UVM is unavailable.

Host signature bootstrap and time policy are independent of UVM-editable settings. Host trust configuration pins the initial Ed25519 public key/key ID and a non-negative integer `initial_maximum_future_skew_seconds` before the first signed policy report can be admitted. The first policy report must pass that pinned skew check; it cannot choose its own trust window. Subsequent reports use the latest accepted policy's skew. Policy revision must strictly increase; same revision with identical digest is an idempotent replay only when report identity and canonical bytes also match, and same revision with different digest or any lower revision is rejected. A `policy` report's `desired` is exactly `null`; a `status` report's `desired` is the current pair or null before configuration.

`POST /recovery-control/v1/{deployment_id}/reports` accepts exactly this signed union DTO. A `policy` report updates only policy trust/readback and must set desired/application/archive/freshness/restore and `recovery_epoch` to `null`; a `status` report carries the latest independent state and a non-negative integer epoch. Both include signed clock inputs and full freshness/skew policy:

```json
{"schema_version":1,"deployment_id":"g7-local","report_id":"<uuid>","sequence":9,"controller_instance_id":"<uuid>","report_kind":"policy","host_policy":{"revision":3,"digest":"sha256:<64-lowercase-hex>","bounds":{"interval_seconds":{"min":60,"max":604800},"timeout_seconds":{"min":1,"max":86400},"maximum_backup_age_seconds":{"min":60,"max":31536000},"restore_verification_timeout_seconds":{"min":1,"max":604800}},"archive_target_refs":["archive-target-local-a"],"recovery_profile_refs":["recovery-profile-local-a"],"maximum_report_age_seconds":300,"maximum_future_skew_seconds":30},"desired":null,"settings_application":null,"completed_archive":null,"freshness":null,"restore_verification":null,"recovery_epoch":null,"observed_at":"2026-10-27T12:00:00Z","fresh_until":"2026-10-27T12:05:00Z","signature":{"algorithm":"Ed25519","key_id":"host-controller-key-1","value":"<base64url-signature>"}}
```

For `report_kind:"status"`, `settings_application` is the exact object `{"state":"pending|applied|failed|uncertain|unknown","requested_revision":2,"requested_digest":"sha256:<64-lowercase-hex>","intent_id":"<uuid-or-null>","host_policy_revision":3,"active_revision":1,"active_digest":"sha256:<64-lowercase-hex-or-null>","reported_at":"<UTC-time-or-null>","failure_code":"<sanitized-code-or-null>"}`. The requested pair must match the current desired pair to update its state. A command commit creates `pending`; a matching signed host acknowledgement/report can advance it to `applied`, `failed` or `uncertain`; `applied` requires requested and active pairs equal the current desired revision/digest. A report about an older request is retained as history and cannot change the current application projection. `completed_archive` is exactly `{"archive_id":"<uuid-or-null>","completed_at":"<UTC-time-or-null>","manifest_digest":"sha256:<digest-or-null>","outcome":"complete|failed|uncertain|null"}`. `freshness` is exactly `{ "state":"fresh|stale|unknown", "evaluated_at":"<UTC-time-or-null>", "age_seconds":<nonnegative-integer-or-null>, "basis_completed_at":"<UTC-time-or-null>", "maximum_backup_age_seconds":<integer-or-null> }`; for a known effective revision, the reported maximum must exactly match that revision's value and age is receive/evaluation time minus the verified manifest's `completed_at`. `restore_verification` is exactly `{ "state":"verified|failed|uncertain|unknown", "archive_id":"<uuid-or-null>", "recovery_epoch":<integer>, "verified_at":"<UTC-time-or-null>", "failure_code":"<sanitized-code-or-null>" }`. A policy-only report cannot change application, archive, freshness, verification or epoch projections.

`POST /recovery-control/v1/{deployment_id}/acks` accepts exactly `schema_version`, `deployment_id`, `ack_id`, `sequence`, `controller_instance_id`, `intent_id`, `requested_revision`, `requested_digest`, `active_revision`, `active_digest`, `host_policy_revision`, `outcome`, nullable `failure_code`, `observed_at`, and `signature`. Outcome is `applied`, `failed` or `uncertain`. `applied` is valid only when requested and active revision/digest are identical to the current desired revision/digest; otherwise it is rejected and the state remains pending/uncertain. Its success response is exactly `{"schema_version":1,"deployment_id":"g7-local","ack_id":"<uuid>","sequence":9,"accepted":true,"application_state":"applied|failed|uncertain","requested_revision":2,"requested_digest":"sha256:<64-lowercase-hex>","active_revision":2,"active_digest":"sha256:<64-lowercase-hex>","revisions":{"configuration":2,"policy":5,"authority":7,"host_policy":3},"accepted_at":"<UTC-time>"}`. On exact replay return the same response; conflicting ack ID is 409.

`POST /recovery-control/v1/{deployment_id}/recovery-events` accepts exactly `schema_version`, `deployment_id`, `event_id`, `sequence`, `controller_instance_id`, `recovery_epoch`, `connector_recovery_id`, `previous_epoch`, `event_type`, `archive_id`, `manifest_digest`, `source_image_digest`, nullable `target_image_digest`, nullable `new_volume_ids`, `verification`, `queue_inventory_digest`, nullable `public_readback_digest`, nullable `failure_code`, `observed_at`, and `signature`. `connector_recovery_id` is a UUID distinct from integer `recovery_epoch`. `new_volume_ids` is null until allocated, otherwise exactly `{"postgres_cluster":"<opaque-volume-id>","ce_media":"<opaque-volume-id>","uvm_state":"<opaque-volume-id>"}`. `verification` is exactly `{"uvm_public_api":"not_run|passed|failed","ce_public_api":"not_run|passed|failed","media_readback":"not_run|passed|failed","queue_reconciliation":"not_run|passed|failed","migration":"not_run|passed|failed","details_digest":"sha256:<digest-or-null>"}`. `event_type` transitions are `restore_started` (must advance external epoch floor exactly by one), `preflight_rejected` (only for that admitted epoch), `volumes_restored`, `verification_passed`, `verification_failed`, `fence_released`; only the ordered transitions are accepted. Failed/rejected restore keeps the epoch floor advanced and startup fenced. Response is exactly `{"schema_version":1,"deployment_id":"g7-local","event_id":"<uuid>","sequence":10,"recovery_epoch":1,"accepted":true,"current_state":"started|preflight_rejected|restored|verified|failed|released","revisions":{"configuration":2,"policy":5,"authority":7,"host_policy":3},"accepted_at":"<UTC-time>"}`. Same event ID and canonical bytes replays this exact response; changed bytes conflict. No transition may release ingress/effects except `fence_released` after the required signed readback and reconciliation evidence.

The external host control plane persists `{deployment_id, recovery_epoch_floor, controller_instance_id, last_sequence}` outside the application database and all three Docker volumes. It authenticates the controller with mutual TLS and returns a checkpoint over that authenticated channel. After detecting database rollback or a lower restored epoch, the controller sends `POST /recovery-control/v1/{deployment_id}/sequence-resync` over mutual TLS with exactly `schema_version`, `deployment_id`, `resync_id`, `controller_instance_id`, `database_epoch_seen`, `database_sequence_seen`, `checkpoint_epoch_floor`, `checkpoint_last_sequence`, and `issued_at`. UVM binds the request to the authenticated controller certificate, deployment, fresh timestamp and monotonic checkpoint, then atomically stores the higher epoch floor and sequence base; it never accepts a caller-selected lower or arbitrary sequence. Response is exactly `{"schema_version":1,"deployment_id":"g7-local","resync_id":"<uuid>","recovery_epoch_floor":1,"next_sequence":11,"accepted":true,"revisions":{"configuration":2,"policy":5,"authority":7,"host_policy":3},"accepted_at":"<UTC-time>"}`. Before sending any subsequent report, the controller durably stores this exact request/acknowledgement pair in its external host journal. A lost response is retried with the same `resync_id` and exact body; UVM returns the retained response. Changed content conflicts. If the external checkpoint or mutual-TLS identity is unavailable or inconsistent, reports remain rejected and startup/effects stay fenced. The transport acknowledgement is not a payload signature; all report and recovery-event signatures remain Ed25519 as specified below.

Every signed report, acknowledgement, recovery event, startup-fence token and archive manifest carries `signature` exactly as `{"algorithm":"Ed25519","key_id":"<pinned-key-id>","value":"<unpadded-base64url-64-byte-signature>"}`. Canonical bytes are RFC 8785 JSON Canonicalization Scheme UTF-8 encoding of the whole object with the `signature` member omitted; reject duplicate member names, non-finite values, floating-point numbers and invalid UTF-8 before canonicalization. Ed25519 signs/verifies those bytes. The pinned key ID maps to a 32-byte Ed25519 public key in independently managed host trust configuration, not UVM-editable settings. Reports expose only sanitized error codes, digests, times and opaque IDs, never credentials, archive paths, payload data or raw exception text.

Identical report ID and bytes replay idempotently. Same ID with changed bytes conflicts. Require the next durable per-controller sequence (an exact accepted replay is the only exception), registered controller instance, deployment match, valid Ed25519 signature, canonical digest, and `observed_at` no later than trusted receive time plus the **previously trusted** `maximum_future_skew_seconds`. A policy report is itself fresh only while trusted receive time is no later than `observed_at + maximum_report_age_seconds`; an expired policy report is retained for history but cannot authorize a write or change current policy. The signed `fresh_until` must equal `observed_at + maximum_report_age_seconds`; disagreement invalidates the report. A status report may use the last accepted fresh policy and cannot change policy limits. A late/stale status may be retained as history but cannot regress current effective revision, archive freshness or recovery epoch. Gaps, signature errors, cross-deployment requests and stale epoch reports cannot advance public current state. Persist accepted report and projection atomically. Public policy freshness is computed from signed policy `observed_at` and receive time using its signed maximum report age and previously trusted skew; no snapshot, expired snapshot, untrusted clock or future-time anomaly yields `unknown` (expired valid snapshot may be displayed as `stale`). Archive freshness is a separate computation from signed `completed_at` against the `maximum_backup_age_seconds` of the verified effective settings revision; it never uses desired age or report age.

Every successful `POST /recovery-control/v1/{deployment_id}/reports`, including exact replay, returns the same acknowledgement DTO: `{"schema_version":1,"deployment_id":"g7-local","report_id":"<uuid>","sequence":9,"accepted":true,"report_kind":"policy|status","policy_revision":5,"authority_revision":7,"host_policy_revision":3,"policy_digest":"sha256:<digest>","desired_revision":2,"desired_digest":"sha256:<digest>","accepted_at":"<UTC-time>"}`. `desired_revision` and `desired_digest` are both null for policy-only reports or before initial settings. Persist this acknowledgement beside the exact signed report so replay returns identical content. A conflicting report ID returns 409 and no projection changes.

`POST /recovery-control/v1/{deployment_id}/connector-quarantine` accepts exactly `{"schema_version":1,"deployment_id":"g7-local","event_id":"<uuid>","recovery_epoch":1,"connector_recovery_id":"<uuid>","connector_id":"<stable-connector-id>","intent_ids":["<uuid>"],"reason_code":"restore_uncertain_effect","observed_at":"<UTC-time>","signature":{"algorithm":"Ed25519","key_id":"<pinned-key-id>","value":"<unpadded-base64url-signature>"}}`. It durably marks only those named intents quarantined and non-dispatchable under that recovery UUID/epoch. Success and exact replay return `{"schema_version":1,"deployment_id":"g7-local","event_id":"<uuid>","accepted":true,"recovery_epoch":1,"revisions":{"configuration":2,"policy":5,"authority":7,"host_policy":3},"accepted_at":"<UTC-time>"}`. Changed content conflicts. There is no unquarantine, dispatch, or general state mutation operation on this listener.

Host bounds and opaque refs are provisioned outside UVM. Public readback may disclose the bounded numeric limits and refs allowed for that deployment, but never registry metadata, credentials or storage locators. Bounds/policy snapshots are signed and time-bounded. A settings write is accepted only with a currently fresh signed policy snapshot; there is no stale-policy exception. Host policy is authoritative for acceptance in all cases.

## Cold capture consistency point

The pinned `Dockerfile.g7` declares exactly these three Docker volumes: `/var/lib/postgresql/data`, `/app/media`, and `/opt/uvm/state`. The first is one PostgreSQL cluster containing separate UVM and DefectDojo databases with distinct least-privilege database roles; it is captured once as a single member, never represented as two PostgreSQL volumes. The other members are DefectDojo media and UVM state. The controller compares runtime mounts and image declaration to this exact allowlist; missing, extra, duplicate or remapped members abort capture. Valkey has no declared durable volume. Before stopping it, the controller closes task admission, stops dispatchers, drains queued/reserved/in-flight Celery tasks to completion where possible, and records an inventory of every task ID and corresponding UVM/CE durable intent or completion receipt through supported interfaces. It does not archive a live Valkey memory image as durable state. Any task that cannot be proven complete or safely not-started remains in a signed unresolved inventory. The ordinary post-capture restart must reconstruct all safely retryable tasks and reconcile the unresolved inventory before releasing the fence; it may not discard volatile queue work merely because the volume snapshot succeeded. Image digest, package-manifest digest and exact volume identities are recorded in the archive manifest.

At the consistency point the independent host first fences ingress and all external effects, then stops UVM workers/schedulers and DefectDojo writers, drains and journals Valkey work as above, then cleanly stops the single PostgreSQL server process after both database roles are quiescent. It captures immutable snapshots of all three stopped volumes as one archive operation. No database-only live dump, running-writer copy or independently timed volume snapshots qualify as this coordinated cold backup. If fencing, queue reconciliation, any stop or snapshot step fails or times out, no complete archive is published; record failure/uncertainty and leave the deployment fenced until the controller establishes a safe state. After a successful capture, restart uses the same verified image with dispatch still fenced, reconstructs proven pending tasks, reconciles every queue/effect inventory entry, verifies no task or intent was lost, and only then releases the temporary fence. If any entry remains unresolved, retain the fence and require explicit reconciliation.

The signed complete manifest binds schema/version, deployment and archive IDs, archive generation, recovery epoch, capture start and consistency-point times, image and package-manifest digests, all three named volume/member digests and byte lengths, configured settings revision/digest, host-policy revision/digest, controller identity/sequence, exact queue/effect inventory digest, and outcome. The host signs only after all members are durable and independently reread/hash-verified. Missing, extra, duplicate, truncated or digest-mismatched members are rejected. Archive completion time is the consistency-point time, not the settings apply or upload-start time.

## Restore, epoch and startup fence

Restore is a host-controlled state machine. The trusted host keeps a monotonic recovery-epoch floor in its independently durable control journal, outside the three restored volumes and outside the rollback-prone UVM database. On startup and before any listener or worker starts, the controller obtains the authoritative epoch floor and a fresh authenticated controller sequence checkpoint from its trusted control plane. If either is unavailable, it fails closed. A restored UVM epoch below the external floor is never accepted as current. After database rollback, the controller performs the mutual-TLS sequence resynchronization described above and journals the exact acknowledgement before sending reports; it does not rely on a payload signature for that transport acknowledgement. Neither side accepts arbitrary caller-selected sequence resets. This makes report retries replay-safe without depending on a sequence counter that was itself rolled back.

The host selects an explicitly identified signed complete archive and validates signature, deployment, image/package compatibility, exact member set, every member digest/length, and manifest schema before creating or populating any replacement volumes. Validation failure leaves existing and replacement volumes untouched and keeps ingress/effects fenced.

After successful preflight, the external host controller creates three new empty volumes, restores the exact members, and starts the same image digest recorded in the manifest with a fail-closed recovery startup fence. Before starting the container, host network policy denies ingress and all egress except narrowly scoped local health/control-plane paths. The entrypoint requires a signed startup-fence token bound to deployment, target image, new volume identities, archive digest, recovery epoch and host-supplied `connector_recovery_id` UUID; without it, it starts only PostgreSQL, Valkey and the in-container recovery-control process, not application children. The first application-facing socket is the separate recovery-control listener only. The external host controller obtains the external epoch/sequence checkpoint, performs mutual-TLS sequence resynchronization, journals the exact acknowledgement, and submits signed connector-quarantine records for uncertain intents. The in-container recovery-control process validates and durably persists those submissions and gates startup; it does not possess host client credentials, signing keys or the authoritative journal. Only after those steps succeed does it allow dedicated verification-only UVM and CE API modes bound to loopback. These product modes allow only explicitly enumerated GET/HEAD health and readback routes; reject all POST/PUT/PATCH/DELETE routes, write-capable hooks, webhooks, polling, Celery tasks and administrative actions, even if a route is normally read-only but can create audit or cache state. Authentication/session hooks must not refresh or mutate session state. Automatic and startup-triggered migrations are disabled. Egress to scanners, GitHub, Slack, SIEM, SMTP, OIDC discovery and arbitrary networks stays denied. PostgreSQL is opened for explicit migration only after the pre-migration public readback; that is a host-journal-authorized one-shot migration process, not a product API write. After migration, verification-only mode is restarted and both products are read back again while the fence remains held. The integer `recovery_epoch` is never used as a connector key. The host generates a fresh UUID `connector_recovery_id` per restore attempt, stores its mapping to deployment, epoch and archive in the external journal, and passes that UUID to connector recovery APIs as their idempotency namespace. Neither identifier can be derived from or substituted for the other.

CE's Valkey/Celery queue is reconstructed from the signed queue inventory and restored durable UVM intents, not copied from a stale in-memory queue. Each inventoried reserved/in-flight task is matched to its stable durable intent and classified as safely not-started, completed with receipt, or uncertain. Missing durable intent, ambiguous completion, or a task without a stable idempotency key stays in an unresolved inventory and is not enqueued or resent. Reconstruct only tasks proven not-started and still authorized/current. Completed tasks remain completed; uncertain tasks remain held for explicit reconciliation.

UVM and CE verification uses their supported public APIs and stable retained-state sentinels from the authorized fixture; there are no direct CE database writes. Required checks confirm UVM settings/audit/decisions/mappings/intents and CE findings/engagements/media are readable and consistent with the captured sentinel. Uncertain queued external intents remain quarantined and are never automatically resent; the recovery report identifies them for explicit reconciliation.

On each admitted restore attempt, the host durably advances the external monotonic recovery epoch floor before creating replacement volumes. Signed recovery event/report binds deployment, integer epoch, host-supplied connector recovery UUID, archive ID and manifest digest, source and target image digests, new volume identities, controller identity/sequence, verification outcomes, supported-API readback digest, unresolved queue/effect inventory digest, timestamps and sanitized failure code. Event identity is the tuple `(deployment_id, recovery_epoch, event_id)`; each `event_id` is a UUID and each event consumes the next controller sequence exactly once. At an epoch, the graph is `restore_started -> preflight_rejected` (terminal) or `restore_started -> volumes_restored -> verification_passed -> fence_released`; after `volumes_restored`, `verification_failed` is an alternative terminal event. No other edge, duplicate transition under a new ID, or event after a terminal event is accepted. Exact same event-ID/body replay returns its retained acknowledgement; same ID with changed body conflicts. Stale/lower epochs and conflicting same-epoch content are rejected. Failed verification leaves the replacement fenced and does not roll the epoch back. A new explicit restore attempt receives a new epoch and a new connector recovery UUID.

The controller allows ingress and runtime effects only after supported-API readback succeeds, required migration policy is explicitly satisfied, the paused-effect and CE queue inventories have been reconciled according to the host recovery profile, and a signed epoch report records the result. The release of each fence is a distinct host-journaled transition: local read-only APIs; explicit migrations; queue/effect reconciliation; signed public recovery acknowledgement; ingress allow; then egress/workers allow. Any missing acknowledgement, failed check, stale epoch or sequence uncertainty returns to the closed state. This local v1 proof uses migration pause and explicit migration execution while still fenced; it does not silently enable automatic migrations or dispatchers. Startup health, settings application, archive completion, archive freshness and restore verification remain separate states.

## Public retained-state readback

The decisive readback is through authenticated, permission-scoped public UVM and DefectDojo APIs/UI after replacement startup, never by querying database tables directly. Preserve fixture sentinel IDs and before-capture canonical public responses/digests for UVM retained records, CE finding/engagement records, media retrieval, and queued intent state. After restore, read the same retained identities from the new container; verify values and lineage/assessment/audit/issue associations remain unchanged, CE media is retrievable, and uncertain effects remain held. The signed recovery report links the readback digest and epoch to the archive manifest. Public readback is a local development assertion, not external-service or production recovery evidence.
