# G7 data preservation and audit readback v1

Status: proposed development contract for FR-AU-01, FR-AU-02, G7-AU-01 and G7-RET-01. This is the first contract-review milestone, not implementation, gate approval, elapsed-period evidence, production policy, or a deletion decision. No disposal or pruning is defined. All fixture data and timing are explicitly local and synthetic.

## 1. Objective and boundary

For one exact registered source tuple `(source_family, source_account_id, scope_key)`, establish whether independently inventoried product source evidence, complete UVM audit events, and scanner collection history can be read and matched after replacement of the application container while retained volumes remain. Reports describe the current check only. `elapsed_preservation` is always `unverified` in this increment: logical-age fixtures can exercise classification but cannot prove one year or three months elapsed.

The increment covers source evidence needed to validate detection provenance, all `EVENT_FIELDS` audit records (including administrative and operational events), and scanner collection runs/revisions, attempts, pages, registered evidence and expected-run transitions. It does not cover generic access/application logs, pre-reservation CE import CLI failures, production providers or values, actual scanner/SIEM integration, legal holds, deletion, or general retention settings. DefectDojo remains accessed through supported APIs; this work adds no direct CE database writes.

## 3. Authority and scope selection

Add selectable actions preservation.read and preservation.evidence.read to the current server-side permission catalogue. Add separately grantable audit.read.deployment, scoped by exact deployment ID, for deployment-wide/non-group audit targets only. They are separately grantable and denyable. Authorization is reevaluated on every request using the authenticated current principal, active memberships, complete current grants, configured grantable source-scope ceiling and all applicable explicit denies. On the server, a grant is eligible only when one complete grant contains both the requested action and exact tuple; do not union an action from one grant with a tuple from another. Session ceilings and revocation take effect immediately. Bootstrap administrator status alone does not imply either action.

The browser obtains candidate tuples from existing GET /api/v1/auth/session, fields source_scopes and authority.group_scopes. Each tuple is the exact three-string array [source_family, source_account_id, scope_key]. The UI treats every returned tuple as a candidate and submits the selected exact tuple to GET /api/v1/operations/preservation. That GET alone establishes permission and returns the same non-disclosing 404 for a denied or absent tuple. The browser does not reconstruct action grants, denies or eligibility from session fields, and there is no extra entitlement/projection route. GET /api/v1/assessment/administration/catalogue exposes the grantable envelope only; it is not a selector. Do not accept wildcard selectors.

For source tuple T, preservation action matching requires the grant's exact source scope T and action in the same complete grant. An explicit deny wins when its principal/group matches the current authority and its action and target scope cover T. The server computes authority_fingerprint as SHA-256 of canonical principal ID, credential mode, session/link IDs and revisions, policy/mapping/group revisions, active grant IDs/revisions with paired actions and scopes, applicable deny IDs/revisions/scopes, and effective session ceiling. The audit_authority_fingerprint hashes the corresponding current audit.read and audit.read.deployment grants/denies, deployment scope and event-target attribution revision. Expose only these digests and mask reasons, never raw grant/deny documents. Do not map a vulnerability group UUID or generic audit.export target to a source tuple implicitly. For non-session credentials, use the complete configured service credential scope and action as one authority record. A direct request for an absent or unauthorized tuple returns the same 404 not_found envelope, with no counts, provenance or existence distinction. Invalid syntax is 400 invalid_request; unauthenticated is 401; stale/invalid session or CSRF follows existing 403 policy. Authority or policy dependency failure is 503 dependency_unavailable and never returns cached counts as fresh.

Audit class summary and record pages require exact-tuple preservation.read plus current audit.read for every source-targeted event target, and a separately grantable audit.read.deployment action scoped to the exact deployment ID for deployment-wide or non-group targets. A deployment-wide row never passes because its group target set is empty: empty target sets grant nothing. The deployment permission is checked independently from source tuple authority. Deployment-wide administrative/operational events are explicitly attributed to every covered tuple by the signed baseline with attribution deployment; source-targeted events carry exact tuple attribution resolved from retained immutable source identity/provenance. Deleted targets retain captured attribution and remain expected members. If any target or attribution is not provable or audit.read.deployment is absent for a deployment-wide event, mask the whole audit class: counts, oldest time, baseline digest, audit-copy fields and per-record provenance are null or absent as specified below, state unknown, reason audit_scope_incomplete; the records endpoint returns the same 404 used for absent/unauthorized snapshot/class. Never reveal partial totals or whether omitted members exist. The evidence endpoint additionally requires separately selectable preservation.evidence.read on the exact source tuple. Audit payload content is never returned by preservation endpoints. Existing viewer/export routes are unchanged; browser audit.read is not broadened to deployment export authority.

## 4. Public v1 endpoints

All endpoints are GET-only and read-only. They never initiate collection, export, repair, anchor creation, or baseline creation.

| Endpoint | Result |
| --- | --- |
| `GET /api/v1/operations/preservation?source_family=…&source_account_id=…&scope_key=…` | One current report for the exact tuple. |
| `GET /api/v1/operations/preservation/records?snapshot_id=…&class_id=…&limit=…&cursor=…` | One deterministic page from the immutable report snapshot. |
| `GET /api/v1/ingestion/runs/{run_id}/revisions/{revision}` | Immutable historical run revision and its attempts/pages/evidence registrations under exact tuple authority. |
| `GET /api/v1/operations/preservation/evidence/{evidence_id}` | Verified registered evidence bytes under exact tuple and `preservation.evidence.read`. |

`schema_version` is integer `1` (booleans rejected). UTC timestamps are RFC3339 strings ending in `Z`. Unknown query parameters are rejected. Responses use the existing correlation/error envelope and `Cache-Control: no-store`. A check failure is represented in the class state/reason, not converted to empty success. Dependency outage before a coherent report can be produced returns 503. Historical run endpoint is immutable: it never substitutes latest revision for the requested revision. Missing and unauthorized rows are indistinguishable 404.

## 5. Summary, classes and exact null semantics

The public API is an authorization-masked projection of a signed, principal-neutral observation. Its envelope adds response_at, current authority_fingerprint and audit_authority_fingerprint, mask_reasons and current authorization state; these fields are not signed facts. If the caller lacks complete audit.read plus audit.read.deployment coverage, audit_authority_fingerprint is null and all audit class fields are masked as in section 3. Signed checked_at is the independent observer's actual read time. Repeated GETs return the same observation identity and checked_at. GET never stamps a new check time or creates a report. With no valid report, snapshot_id, checked_at, valid_until, baseline_digest and class counts are null; classes are unknown with baseline_missing/trust reason. response_at is present because it describes this API response, not evidence freshness.

Summary shape:

    schema_version: 1
    scope: {source_family, source_account_id, scope_key}
    snapshot_id: UUID or null
    checked_at: UTC timestamp or null
    response_at: UTC timestamp
    valid_until: UTC timestamp or null
    authority_fingerprint: sha256 digest
    audit_authority_fingerprint: sha256 digest or null
    mask_reasons: sorted bounded reason codes
    environment: explicit configured label or null
    classes: exactly the three required class DTOs
    uncovered_classes: sorted unique class IDs whose state is not verified
    elapsed_preservation: unverified

The environment label comes from explicit installation/fixture configuration, is never inferred from hostname and never defaults to production. Missing label is null and yields unknown/environment_unlabelled.

Exactly three class IDs are required: product.source_evidence (minimum_period P1Y), product.audit_history (P1Y), and operational.scanner_collection (P3M). Class DTO is exactly: class_id, minimum_period, state, reasons, expected_records, verified_records, missing_records, changed_records, unreadable_records, unexpected_records, oldest_retained_at, baseline_digest, audit_copy. State is verified|gap|unknown|failed. Reasons are a sorted unique subset of section 11. Counts are nullable non-negative integers. oldest_retained_at is a nullable UTC timestamp; baseline_digest is nullable sha256:<64 lowercase hex>. audit_copy is required and null for source_evidence and scanner_collection. For audit_history it is exactly: state, reasons, expected_events, matching_events, missing_events, changed_events, unexpected_events, expected_receipts, matching_receipts, missing_receipts, changed_receipts, unexpected_receipts, pending_receipts, checked_at. Its state is verified|gap|unknown|failed; counts follow class count nullability; checked_at is the signed independent read time or null.

Null means not established, never zero. Every class count is null together if no trusted complete baseline exists, report expired, authority masking applies, dependency failed during that class read, or the class read did not finish. No partial class counts are exposed. For a complete trusted baseline and complete read, expected_records is the exact signed expected member count. Expected outcomes partition exactly: verified + missing + changed + unreadable = expected. unexpected_records is reported separately for current source members absent from expected membership. A record is exactly one observed outcome: verified; missing (expected key absent); changed (identity/content/provenance mismatch); unreadable (present but bytes/dependency cannot be read); or unexpected (observed but not expected). An unreadable member is not also changed. Counts reconcile mechanically. oldest_retained_at is the oldest verified retained timestamp only when every expected member has a trusted timestamp, otherwise null. baseline_digest is null unless a valid baseline is selected. Incomplete execution makes all class and audit-copy counts null.

State matrix and precedence: absent/untrusted/incomplete/expired baseline or masked authority is unknown with every count null. With a trusted complete baseline, an incomplete class read caused by a dependency is failed with every count null, even if partial observations suggest a gap. For a complete trusted read, any established missing/changed/unreadable/unexpected member or required receipt/anchor anomaly makes the class and audit_copy gap, even when an unrelated first acknowledgement is pending. If a complete read has no established anomaly but has pending_receipts > 0, audit_copy and audit_history are unknown with source_checkpoint_missing; pending alone prevents verified. Only a complete trusted read with no established anomaly and no pending receipt is verified. For non-audit classes, the same ordering applies without audit_copy/pending. This resolves the precedence: trust/masking unknown first; incomplete read failed next; complete-read established gap next; pending-only unknown next; verified last. Empty expected scope is unknown unless a trusted complete baseline explicitly records a legitimately empty scope; that may be verified only for its capture instant and says nothing about pre-baseline history. Expired reports cannot claim fresh verified readback.

Audit-copy counts compare signed expected event and receipt memberships to independent anchor inventory and sink payload/receipt readback. With a complete read, expected_events = matching_events + missing_events + changed_events; expected_receipts = matching_receipts + missing_receipts + changed_receipts. pending_receipts counts known unanchored sink commits awaiting a first source acknowledgement; it is outside expected_receipts because no receipt has yet been established as immutable expected membership. pending_receipts is null unless the complete source/sink read establishes it. A positive pending count alone makes audit_copy unknown with source_checkpoint_missing; established receipt/anchor anomalies still take gap precedence. Unexpected event/receipt counts are separate and never added to expected totals. verified requires exact expected sets and canonical payload equality. Missing, extra or changed copy/receipt is gap; unavailable/incomplete trust inventory is unknown; current dependency outage/incomplete read is failed with all counts null. Extra sink-only rows are unexpected and are never appended to expected membership by reconciliation. No source-row-only calculation may mark the copy verified.

## 6. Snapshot, report freshness and pagination

A signed report binds UUID snapshot, exact source tuple, class definitions/version, baseline ID/digest, deployment ID, current recovery epoch, replacement/storage generation, source and sink watermarks, signed check time and configured freshness interval. The signed report is principal-neutral: no caller identity, grants, redactions, cursor or API masking. The API envelope separately adds response time, current authority fingerprints, mask state and cursors; it may omit/null fields according to current grants but cannot alter signed bytes. Local fixture freshness is 300 seconds only when explicitly set; it is not a production default. valid_until is the minimum of configured freshness, signed key validity and deployment trust validity. Missing freshness configuration yields unknown. Signed report recovery epoch/storage generation must match independently trusted current generation. Replacement does not change record keys or original retained timestamps.

Page size defaults to 50 and is bounded 1–100. Rows sort by (record_kind, record_key) using bytewise UTF-8 order; duplicates are rejected. record_key is opaque, stable, non-secret, maximum 512 UTF-8 bytes, contains no control characters and is unique within class/snapshot. Page DTO is exactly schema_version, snapshot_id, class_id, items, next_cursor. Each item is exactly record_key, record_kind, retained_at, state, reasons, expected_sha256, actual_sha256, record_sha256, readback_url; nullable values are explicit. record_kind is class-specific as enumerated in section 8. expected_sha256 and actual_sha256 are raw-byte digests only for byte-bearing members; record_sha256 is the canonical record preimage digest. Item state is verified|missing|changed|unreadable|unexpected. Unknown coverage is expressed at class level, never by fabricating item rows. readback_url is null or a same-origin relative evidence endpoint path.

For a records request, first resolve and authorize the requested snapshot/class resource from the explicit snapshot_id and class_id without reading cursor claims; absent or unauthorized resource is 404. Then validate cursor encoding/shape and HMAC-SHA-256 with the application-held cursor key. Invalid/tampered token is 400 invalid_cursor. Only after a valid MAC may the server interpret claims and compare principal, tuple, class, snapshot, page size, last sort key, signed report digest, authority fingerprint and expiry. A changed authority fingerprint or any binding mismatch is the adopted 400 invalid_cursor (never 409 authority drift); expired token is 409 cursor_expired; expired/replaced signed report snapshot is 409 snapshot_expired. Re-evaluate grants and denies on every request before cursor diagnostics; revoked/unauthorized resource remains 404. Never restart page one or splice snapshots. There is no report-ID endpoint and no 410 response. Responses and cursors use no-store.

## 7. Evidence bytes and file safety

Original source payload bytes live only under durable /opt/uvm/state/source-evidence, directories mode 0700 and regular files mode 0600, with maximum 16 MiB per object in the disposable fixture. This is a development safety bound, not production policy. Create staging files relative to a pre-opened directory fd with exclusive creation and O_NOFOLLOW, stream within the bound while hashing, fsync the file, then publish atomically using renameat2(RENAME_NOREPLACE) or equivalent same-filesystem no-replace primitive and fsync the directory. If the content-addressed final object exists, verify regular-file type, size and digest: exact same bytes permit idempotent reuse; any mismatch is hard conflict/quarantine. Never replace an existing object. Commit DB registration only after published bytes verify. Crash recovery may leave an unregistered orphan; never serve it and report a bounded operational failure for safe reconciliation.

Store opaque generated object IDs and verified digest/size/kind metadata. Resolve IDs through registration and content-addressed filename; accept no caller path, URL or traversal token. Open with openat/directory fd and O_NOFOLLOW; require service UID ownership, regular file and restrictive mode. Check size, read the entire bounded object into a mode-0600 spool or verified immutable byte buffer, hash and compare actual bytes with registered raw digest, expected raw digest and size. Only after success commit HTTP 200 headers/body, streaming those same verified bytes. Never stream before verification. Missing object for an authorized existing registration returns 409 evidence_missing; digest/size mismatch returns 409 evidence_changed; symlink, nonregular file, wrong owner/mode or unsafe path returns 409 evidence_unreadable; absent registration or unauthorized ID is 404; unavailable filesystem or database metadata dependency is 503 evidence_store_unavailable. No error includes partial bytes. Do not expose path, inode, private content or cross-scope existence. Success returns exact bytes with Content-Type application/octet-stream, exact Content-Length, Content-Digest sha-256 structured field, X-Content-Type-Options nosniff and generated opaque attachment filename. No digest-only success.

## 8. Source inventory, canonical records and trust protocol

The independently controlled inventory service owns signing key and storage/credentials; application and CE receive verifier public key only. Use Ed25519 signatures over UTF-8("VOLT-G7-PRESERVATION\0" || purpose || "\0" || canonical_json(payload)). Canonical JSON is UTF-8, sorted object keys, compact separators, no NaN/Infinity, UTC timestamps normalized to Z, UUID lower-case canonical, SHA-256 lowercase. Canonical record digest is SHA-256 over UTF-8("VOLT-G7-RECORD\0" || class_id || "\0" || canonical_json(record_preimage)). Raw byte digest is SHA-256 of exact retained bytes and is never substituted for record digest. Registration digest is SHA-256 over canonical registration metadata and binds opaque evidence ID, raw digest, size, kind and owning immutable source key.

Each signed stream head namespace is the exact tuple (deployment_id, purpose, source_family, source_account_id, scope_key, class_id); thus each of the three class baselines and each class readcheck has an independent monotonic sequence and genesis. Each head begins with its own deployment-provisioned signed genesis record at sequence zero, with genesis digest pinned independently of the application. Each next record is exactly previous sequence+1 and names that namespace head digest. Verifier checks against the independent store head. Re-reading the identical current sequence/digest is idempotent and valid; a different digest at that sequence, lower sequence, skipped sequence, missing predecessor, broken chain or conflicting head is unknown. GET never advances or alters heads. Failed publication retries identical deterministic ID/canonical bytes; conflicting bytes require independently authorized new publication after incident disposition, never overwrite. A class report binds its class baseline and deployment recovery/storage generation. One summary snapshot composes exactly one valid current report for each of the three class namespaces plus the three selected baseline digests, tuple and generation. Summary checked_at is the minimum (oldest) of the three signed class checked_at values; valid_until is the minimum of the three class valid_until values. If any class time is unavailable, summary checked_at/valid_until are null and the affected classes remain unknown. snapshot_id is deterministic UUIDv5 over contract namespace and canonical tuple + generation + ordered (class_id, inventory digest, report sequence, report digest) triples. Repeated GET of unchanged heads returns the same snapshot and class checked_at values. Any class head advance yields a new summary snapshot; old page cursors expire and no class report is spliced across generations. Recovery/storage generation is a separately signed deployment-controller value; each report binds deployment ID, recovery epoch, generation UUID and volume-set digest. On replacement, generation advances before readback, then independent observer publishes new class reports against preserved inventory and actual readback.

Expected inventory payload includes contract ID/version, deployment, schema-head digest, exact tuple/class, inventory sequence and predecessor, capture ID/time, source watermark, completeness declaration, key ID/validity and members. Audit members store event identity/sequence, expected digest, anchor canonicalization version and safe representation metadata only; raw audit payloads and exact canonical event preimages are never embedded in the inventory or exposed through manifest/readcheck APIs. Report payload includes same deployment/scope/class bindings, recovery epoch/generation/volume-set digest, inventory digest, report sequence/predecessor, captured watermarks, signed checked_at, validity interval, read outcome and members. Purpose values are exactly expected-inventory-v1 and readcheck-report-v1; keys are purpose/deployment bound. Unknown schema/deployment, bad signature, malformed canonical form, future time beyond configured skew, duplicate member or incomplete scope coverage yields unknown. A later expected inventory may add newly committed expected records only if it preserves all prior expected keys/digests/revisions; it cannot remove or alter expected members. A newly established receipt/linkage/transition/anchor is an appended member under its own stable kind/key, never a changed field in an earlier member. Readcheck never repairs or modifies source/sink/receipt data. Signed manifests/reports are retained privately, restrictive permissions, no raw private payloads.
