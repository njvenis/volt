# G7 exception and ingestion-based SLA implementation contract

Status: local implementation contract for the ingestion-based SLA and risk-exception workflows. It does not select production policy values or establish production integrations, release readiness or G7 completion.

## Draft: identity workload context for SLA selection

This section is a proposed contract for independent review only. It is not implementation approval. Existing `RuleV1` rules with no context fields must keep their current behavior and stored identity unchanged.

### Rule shape and immutable definition

Add the optional keyword-only field `workload_context_fields: tuple[str, ...] = ()` to `RuleV1`. The argument must be an actual tuple. Each name must be an actual string, non-empty, already trimmed (`name == name.strip()`), unique in the tuple, disjoint by exact string equality from `workload_match_fields`, and not an ephemeral locator/host field. Reject invalid names; never strip, sort or deduplicate them. Tuple order is significant. The default is the empty tuple. A non-empty context definition is a new immutable rule definition and requires a new `rule_version`; a provisioned `(rule_id, rule_version)` can never change its match fields, context fields or verified-locator setting.

Context fields describe retained workload facts that downstream policy selection may read. They do not prove workload correspondence. The resolver SHALL use only `workload_match_fields` to find candidates, select a workload, decide `matched` versus `new`, or justify rebuild continuity. Context fields SHALL NOT contribute candidate evidence, disambiguation, workload creation, or incarnation/exposure correspondence. A context-only observation with no usable match field remains unresolved and creates no workload or exposure. Shared context such as `environment=local` therefore cannot select one of several native workloads.

Context values are read from the existing canonical `matching_inputs` string map. A present context value must be an actual non-empty string; whitespace-only values are invalid. Preserve every accepted value exactly: do not trim, case-fold, sort or otherwise normalize it. An omitted key is missing. Inputs whose names are not declared as either match or context fields remain in resolution provenance/fingerprinting but are neither persisted as workload context nor used as identity evidence.

Resolve candidates using only the pinned `workload_match_fields`. If match evidence is ambiguous, keep it ambiguous; context cannot filter candidates into a winner. Only after a unique match-evidenced workload has been selected may the resolver compare supplied context with that workload. A supplied value that disagrees with an already retained value makes the resolution `unresolved` with a specific context-conflict explanation. It cannot overwrite context or proceed to rebuild, occurrence, membership, episode, receipt, evaluation or clock effects. A context veto must not persist staged group/CVE/workload/incarnation/exposure/occurrence graph changes. Retain the unresolved resolution evidence and already committed source observation/retention receipt honestly; source retention is a separate transaction and is not undone by a later resolution failure. Preserve all existing native-key, linked-observation, historical-alias, locator-verification and correction-authority guards.

On a genuinely new workload selected using at least one valid match field, persist the supplied non-empty context values in `workloads.stable_attrs` alongside the match values. On a matched workload, a supplied context value equal to retained context is accepted without mutation. An omitted value does not clear or weaken existing retained context; the stored value remains usable for SLA policy selection. If stored context is absent, a later supplied value does not enrich or backfill the workload; that field remains unavailable for policy selection. A missing field is a public coverage gap only when an applicable prospective G7 policy requires that selector and the retained authoritative workload context cannot supply it. Missing an optional context field that no applicable selector requires does not blanket-invalidate coverage. Context conflict on a new observation creates no new SLA coverage and does not erase, reset or invalidate an already admitted membership's trustworthy clock or coverage. Any separate authorized context/identity correction or clock invalidation remains governed by its existing exact-target guards; this draft adds no correction workflow and does not weaken existing authority.

Policy selection uses context retained by the authoritative identity writer, never browser-supplied or report-supplied values. This rule is prospective: an episode already pinned to G5 stays G5, including later membership in that same episode, regardless of a subsequently published G7 policy or missing context. Only a subsequent eligible G7 episode evaluates its required selectors against retained context. Missing a required selector for that prospective G7 selection is a gap; absence of a selector not required by the applicable policy is not. The browser does not synthesize context or calculate coverage.

### Compatibility, persistence and replay

Persist `workload_context_fields` as a non-null JSON array with database default `[]` on `identity_rule_definitions`. Proposed Alembic migration `0062` adds only that column. Existing rows receive `[]`; migration does not rewrite rule versions, digests, resolution inputs, request fingerprints, workload attributes, episodes, receipts, SLA evaluations or reports. The ORM/bootstrap metadata and the migration must describe the same exact column type, nullability and default for each supported dialect.

Pin both non-empty canonical preimages exactly. The current definition preimage is the compact, sorted-key JSON object `{"fields": MATCH_FIELDS, "verified_asset_locator": VERIFIED}`. For non-empty context, append exactly `"workload_context_fields": [ORDERED_CONTEXT_NAMES]`; for empty context, omit that member entirely, preserving current bytes. Serialize with the existing Python `json.dumps(..., sort_keys=True, separators=(",", ":"))`, UTF-8 encode, then SHA-256 hex digest. For example, fields `("provisioning_key", "service_key")`, `verified_asset_locator=True`, context `("environment",)` serialize exactly as `{"fields":["provisioning_key","service_key"],"verified_asset_locator":true,"workload_context_fields":["environment"]}`. The legacy empty-context preimage `{"fields":["provisioning_key","service_key"],"verified_asset_locator":true}` must retain SHA-256 `6ad174d7105acaa0f301671dad9bf4ff93e5b51a31dee5ebc84764959faf9bf7`.

The existing request-fingerprint preimage is the compact, sorted-key JSON object with exactly `observation_id`, `observation_revision`, `rule_id`, `rule_version`, `rule_fields`, `verified_asset_locator`, `matching_inputs` and normalized `evaluated_at`. For non-empty context only, append exactly `workload_context_fields` with its ordered names; for empty context omit that key entirely. Serialize with the existing `json.dumps(..., sort_keys=True, separators=(",", ":"), allow_nan=False)`, UTF-8 encode, then SHA-256 hex digest. Values remain the exact canonical `matching_inputs` strings. Preserve the existing correction-authorization semantic binding exactly: after this base hash, hash the concatenated base hex string and the existing `_decision_semantics(decision)` encoding as today. Golden implementation cases must assert the legacy definition digest above, old request-fingerprint preimage/hash and exact replay response, and the corresponding non-empty definition/request preimages and hashes. Do not sort or deduplicate names, normalize names or values, or silently repair immutable data.

Persist `workload_context_fields` as a non-null JSON array with database default `[]` on `identity_rule_definitions`. Before constructing a `RuleV1` from stored data, require the stored value to be an actual JSON array/list of unique valid strings disjoint from the stored match-name array. Reject malformed strings, objects, tuples, duplicate names, whitespace-padded names and overlaps; never coerce with blind `tuple(value)`, sort, deduplicate or repair stored data. Context fields never become eligible scalar-correction targets; scalar correction continues to use match fields only. Old rows with migration default `[]` preserve their exact digest, authorization target and replay. Do not recompute old digests during migration or hydrate context from scanner history.

Context persistence, identity resolution, episode creation and authoritative SLA receipt/evaluation remain inside the existing retained-observation transaction. If the receipt/evaluation or any later transaction step fails, no newly created context-bearing workload, resolution head, episode, receipt, evaluation or clock state commits. The already committed source observation/retention receipt remains because source retention is a separate transaction. An unresolved context conflict writes only unresolved resolution evidence; it creates no new identity graph/CVE or occurrence, episode, receipt, evaluation or clock and cannot change an existing workload's context or any previously admitted clock.

## Version and provenance

The existing G5 calculator and issued reports keep their pinned definitions and scanner-observation anchors. The evolved calculator uses a new definition and policy version with separate fields for the start source (`uvm_ingest_commit_v1`) and the duration arithmetic. Missing version fields retain historical G5 meaning; migration must not infer a pause or a UVM ingest time for old records. A report produced under the new definition pins the ingest receipt, clock events, exception decisions and policy revisions used for each atom. A later calculation creates a separately identified report rather than rewriting an issued report.

Activation is prospective and explicit: a versioned policy has an effective instant, and a new episode first retained by UVM at or after that instant uses the evolved clock. Episodes already open and active acceptances at activation retain their G5 semantics until that episode ends. New membership in such an existing episode retains that episode's G5 contract. The first subsequent episode uses the new contract and its own trustworthy ingest receipt. There is no automatic migration of open episodes or acceptances, no migration-time anchor, and no inferred historical pause. Any later exact-target migration needs a separately reviewed command and proven original ingestion provenance before activation; it is outside this local slice.

The authoritative new start is a UVM-server timestamp written with the first durable UVM retention of a positive finding for the applicable membership and episode. The timestamp and immutable receipt are committed in that same transaction; a rolled-back attempt contributes no start. The server obtains the time, never the scanner, collector, client or CE. CE import acceptance and later settlement are separate events. Carry the receipt across reimport, verified rebuild continuity and owner transfer. A newly affected membership gets its own receipt. A successor recurrence retains the original detection history and receives a new SLA anchor from the durable UVM retention of its causal positive. If the receipt or episode correspondence is untrustworthy, show an SLA gap rather than substituting another timestamp.

## Per-atom clock

Each `(episode_id, occurrence_id)` has an append-only clock history. A clock event records the effective time, server-recorded time, transaction order, causal ingest receipt or assessment decision, selected calculator/policy revision, predecessor and exact membership. Store the original deadline and all later evaluations; never replace the original baseline or erase a prior breach interval. Unknown coverage remains unknown.

A versioned exception request stores immutable submitted membership, finding/resource context, rationale, compensating controls, proposed expiry and expected episode/evaluation revisions. The proposed expiry is a suggestion, not an approved limit. The approval command supplies the approver-selected expiry, decision rationale, expected request revision and current authority. The selected expiry must satisfy the approver's configured bounds and separation-of-duties rules. Every approval toward a multi-approver threshold signs the same request revision and selected expiry; changing either requires a linked replacement proposal and fresh approvals. Partial approval does not accept risk or pause the clock. Only the final authorised approval activates the exact current membership. In one UVM transaction, check authority, membership, episode and evaluation revisions, then commit the decision, per-atom pause snapshots, audit event, command receipt and required notification/projection intents. Any failed check or audit write rolls back the whole operation. An authorised, scoped open-request queue shows pending approvals; a scoped register retains proposal, approver-selected expiry, approval instant, decisions and terminal history.

At activation, snapshot each known atom's remaining duration under its selected duration arithmetic, original baseline, applicable pre-pause deadline, prior breach state, approval time and chosen expiry. Supported duration arithmetic remains G5's elapsed UTC seconds, including `calendar_days_utc` as exactly 86,400 elapsed seconds per day. Reject business-day, local-midnight and other unsupported calendars rather than approximating them. Remaining time is never negative; an atom already overdue retains its prior breach and zero remaining time. An atom with no trustworthy deadline remains a gap and cannot gain SLA coverage from an exception expiry.

An effective pause is `[activation, end)`. During it, expiry is the active time target and the frozen SLA remainder is displayed separately. At the end, the new SLA deadline is the effective end instant plus the captured remainder under the same pinned duration arithmetic. A late expiry worker must calculate from the stored expiry, never its processing time. Deadline equality is not overdue; a valid confirmation at exact deadline is on time. At exact expiry, the exception is ineffective and the resumed clock applies. A retained transaction sequence resolves commands with equal timestamps.

## Changes during a pause

- **Early revocation:** An authorised revocation ends the pause at its committed effective time. The captured remainder resumes from that time. Revocation does not remove accepted-risk history or prior breaches.
- **Material-change suspension:** Suspension ends the effective pause at the committed material-change time for affected atoms. Suspended acceptance grants no current protection. A linked replacement needs a fresh authorised approval; it cannot silently reactivate the predecessor.
- **Linked extension or replacement:** Preserve G3's prohibition on unrelated overlapping active acceptances. Only a predecessor in a G3-permitted active or suspended state can be replaced; revoked, expired and rejected decisions are terminal, so a later exception requires a fresh submission. An atomic replacement of a still-effective active predecessor carries the frozen remainder for shared atoms across one uninterrupted pause and changes the expiry target without stacking a second pause or resetting the ingest anchor. If the predecessor is suspended, its clock has already resumed: replacement approval snapshots the **current running remainder**, not the old frozen remainder. Added atoms also snapshot their current evaluation at approval. Removed atoms resume their captured remainder at the replacement instant **only if still paused**; an already running removed atom keeps its current evaluation and deadline. A failed replacement leaves the predecessor and its clock untouched.
- **Remediation:** A valid exact-membership engineering confirmation during a pause completes that atom at the confirmation instant. Its clock becomes terminal; expiry does not reopen it. Accepted risk alone never supplies confirmation or an on-time completion. A genuine confirmation during a pause is reported in a separate `completed_during_exception` count, not as an ordinary on-time success or a late completion caused solely by paused time. Any breach before approval remains in historical breach reporting.
- **Policy, severity or deadline revision:** A paused snapshot is immutable. Configured material severity or exposure change first suspends the acceptance and resumes its captured remainder at that committed instant. Commands that would otherwise change duration or deadline during an effective pause conflict and make no clock change; the authorised actor may terminate the pause, then submit a separately guarded revision against the running evaluation. A deadline extension still requires its independent bounded `sla.deadline.revise` grant, rationale and exact predecessor guards. Acceptance approval never confers that grant. Every permitted later revision retains its own audited evaluation and cannot alter an issued report or erase prior breach history.

## Alerts, reads and proof boundary

The scoped group read at `GET /api/v1/assessment/groups/{group_id}` includes
`assessment.authority_revision` as a required non-negative integer. It is the
native authority revision read from the same database snapshot as the group,
assessment and policy view; legacy authority state reports its actual revision
`0`. G7 v1 submit and approve commands carry that exact value as
`expected_revisions.authority`. A missing or stale value conflicts under the
command transaction and has no effects. The existing scoped `assessment.read`
permission protects this scalar; it does not grant catalogue or administration
access. On conflict, clients refresh the group view, clear stale selection and
acknowledgement, and require re-review and fresh confirmation before retrying.

An authorised configuration selects advance-warning offsets, Slack and/or email channels, destinations, retry rules and recipient scope. Durable intents are uniquely keyed by exception decision, expiry revision, offset, channel and destination. Each channel/destination has independent attempt and outcome history. At dispatch and every retry, recheck that the decision/expiry revision is effective, the affected atom is still outstanding, and the destination remains authorised by current routing and disclosure scope. Replaced, revoked, suspended, expired, remediated or no-longer-authorised warnings are suppressed with a retained reason. An offset already passed when approval becomes effective is recorded as missed and is not sent late unless a separately configured immediate-warning rule applies. Delivery or acknowledgement cannot approve, extend, revoke, resume or confirm remediation. Failures remain visible in scoped UVM health/readback. Actual Slack/email delivery needs separately authorised target evidence; local fixtures are labelled as such.
