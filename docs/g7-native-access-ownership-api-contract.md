# G7 native access and ownership API contract

Status: backend implementation contract for labelled disposable fixtures; no production defaults or gate claim. Covers G7-RBAC-01 / G7-OWN-01 / G7-ID-02.

## Authority mode

`assessment_policy.document.native_authority` is either absent/`legacy` or `{mode: "uvm_native_v1", revision, ownership_revision, activated_at, activated_by, mapping_revision}`. Absence is legacy. Only an explicit audited `native.authority.activate` command changes mode. Native OIDC context derives action groups only from currently effective native access-group memberships and group permissions; provider group claims are provenance only. Ownership-team membership is never an action grant. Bootstrap administrator is a protected grantable-envelope capability, not an assessment action.

## Read endpoints

`GET /api/v1/assessment/administration/catalogue` returns:

```json
{
  "schema_version": 1,
  "authority_mode": "legacy|uvm_native_v1",
  "policy_revision": 1,
  "authority_revision": 0,
  "ownership_revision": 0,
  "selectable_actions": [{"action": "assessment.read", "target_scope": "...", "limits": "..."}],
  "caller": {"principal_id": "...", "can_manage_access_groups": false,
    "can_manage_ownership_teams": false, "grantable": {"actions": [], "target_scope": {}, "limits": {}}}
}
```

`selectable_actions` is generated from the server's action catalogue and the protected caller envelope, never from UI-local values. Each returned item is `{action,target_scope,limits}`; only actions explicitly present in `caller.grantable.actions` (or covered by `"*"`) are returned. The server catalogue universe is `assessment.read`, `audit.read`, `owners.directory.read`, `owners.assign`, `portion.define`, `portion.transfer`, `portion.split`, `routing.override`, `routing.expire`, `severity.override`, `acceptance.submit`, `acceptance.approve`, `acceptance.expire`, `acceptance.reconcile`, `acceptance.reject`, `acceptance.revoke`, `remediation.confirm_portion`, `remediation.confirm_group`, `audit.export`, `github.identity.link`, `github.repository.configure`, `github.commands.preview`, `github.issue.sync`, `github.poll`, `report.create`, `report.read`, `report.export`, `policy.read`, `policy.sla.publish`, `sla.deadline.revise`, `access_group.read`, `ownership.team.read`, and `ownership.team.manage`. Legacy policy mutation and principal administration actions are excluded. `target_scope` carries the explicit scope ceiling with shape `{group_ids,source_families,environments,service_ids,membership_mode}`; selectors are string arrays and `membership_mode` is `explicit|all_current`. `limits` carries the caller's explicit limits ceiling. The caller's `grantable` value is authoritative: `{actions,target_scope,limits,source_scopes,separation_of_duties}`. Empty selectors in the ceiling grant no values; `"*"` grants any value for that selector. `source_scopes` is a list of exact `{source_family,source_account_id,scope_key}` tuples, and each access group must choose a non-empty subset. For non-bootstrap callers `grantable` is empty.

Concrete disposable example (not a product default): `actions:["assessment.read","owners.assign","report.read"]`, `target_scope:{"group_ids":["<group UUID>"],"source_families":["sysdig"],"environments":["production"],"service_ids":["payments"],"membership_mode":"explicit"}`, and `source_scopes:[{"source_family":"sysdig","source_account_id":"<account UUID>","scope_key":"<configured scope>"}]`. The matching limit example is `maximum_acceptance_days:14`, `maximum_severity:"high"`, `whole_group_confirmation:false`, `allowed_environments:["production"]`, `allowed_service_ids:["payments"]`, SLA clock/severity/start-source arrays chosen only from the enumerated values below, `maximum_sla_duration_seconds:86400`, `allow_sla_backfill:false`, `maximum_deadline_extension_seconds:3600`, and `allowed_identity_scalar_fields:{}`. These are example ceiling values; the API response is authoritative for the current caller.

Accepted limit shape is the server catalogue: nullable positive `maximum_acceptance_days`; nullable `maximum_severity` from `critical|high|medium|low|informational`; boolean `whole_group_confirmation`; string arrays `allowed_environments`, `allowed_service_ids`, `allowed_sla_clock_bases` (`elapsed_utc_seconds|calendar_days_utc`), `allowed_sla_severities` (the severity values above), and `allowed_sla_start_sources` (`source_observation_v1|uvm_ingest_commit_v1`); nullable non-negative integer `maximum_sla_duration_seconds` and `maximum_deadline_extension_seconds`; boolean `allow_sla_backfill`; and `allowed_identity_scalar_fields` limited to `identity.workload_field_correct` and `identity.incarnation_locator_correct` (the latter only permits `host_locator`). Values are bounded by `caller.grantable.limits`; the server rejects values outside that envelope. `separation_of_duties` is `{approval_requires_distinct_actor,prohibit_requester_approval,required_approver_count,prohibited_action_pairs}` with booleans, positive integer and action-pair array respectively.

`GET /api/v1/assessment/access-groups` returns `{schema_version, authority_mode, policy_revision, authority_revision, principals, items}`. `principals` contains `{principal_id,display_name,enabled,actor_kind,membership_eligibility:{access_group,ownership_team,reason}}` for persisted identity principals; it excludes service credentials and secrets. A disabled principal has both eligibility flags false and `reason:"principal_disabled"`; an enabled principal has both true and `reason:null`. An item is `{access_group_id, display_name, description, enabled, revision, source_scopes:[{source_family,source_account_id,scope_key}], permissions:[{permission_id,role_id,action,target_scope,limits,separation_of_duties}], memberships:[{principal_id,effective_from,effective_until,enabled,revision}], history:[{event_id,action,actor_id,occurred_at,rationale,before_value,after_value}]}`. The view contains current principals and retained membership intervals, including disabled groups and tombstones, but excludes secret values.

Membership editors use only `principals` returned by the authenticated read. A candidate must have the corresponding eligibility flag true; the command rechecks the persisted identity is still enabled while holding the policy lock. A disabled/unknown principal is ineligible and cannot be added. The membership itself is scoped to exactly one `access_group_id` (or `team_id` for ownership). Access-group authority then remains bounded by that group's retained exact `source_scopes` and each permission's target/limit envelope; team membership records accountability only and grants no action. Provider group claims do not add principals or memberships. The public list is a lookup of configured identities, not proof of the caller's right to edit; each command rechecks caller authority, scope and expected revisions.

`GET /api/v1/assessment/ownership-teams` returns `{schema_version, policy_revision, ownership_revision, items}`. An item is `{team_id,display_name,enabled,revision,memberships:[{principal_id,effective_from,effective_until,enabled,revision}],history:[{event_id,action,actor_id,occurred_at,rationale,before_value,after_value}]}`. Access-group reads require `access_group.read`; ownership-team reads require `ownership.team.read` or `ownership.team.manage` for that team. Both are scope checked on every request and exact replay/readback is rechecked against current authority.

`GET /api/v1/assessment/ownership-teams/{team_id}/principals` is the dedicated picker for ownership-team membership. It returns `{schema_version,team_id,policy_revision,ownership_revision,principals:[{principal_id,display_name,enabled,membership_eligibility:{ownership_team,reason}}]}`. The caller must have current `ownership.team.read` or `ownership.team.manage` for that exact team; it does not require or imply `access_group.read`. It returns configured principal identities only, excludes service credentials and secret values, and marks disabled identities ineligible. Membership commands recheck identity enabled state under the policy lock. A manager may manage membership while having no access-group administration or read grant; ownership-team membership itself still grants no RBAC.

## Commands

Writes use `POST /api/v1/assessment/commands` with the existing envelope `{command_id,action,target_id,membership_ids,expected_revisions,payload}` plus mandatory `payload.rationale` and `payload.evidence_ref`. Policy-level commands use reserved zero UUID target and empty `membership_ids`. Native administration responses use receipt shape `{schema_version,command_id,action,target_id,policy_revision,decision_id,audit_event_id,intents:[{intent_id,kind,target_id,authority_revision,status}],result}`. The stable native `result` is `{effect:"native_administration_state_committed",authority_mode,policy_revision,authority_revision,ownership_revision,object_kind,object_id,object_revision}`; `object_kind` is `authority|access_group|ownership_team|principal`, `object_id` is the stable authority/group/team UUID or configured principal ID, and `object_revision` is the resulting object revision (`null` for a principal update). It describes the committed policy snapshot and is persisted inside `assessment_command_receipts.result`. Exact same-actor/same-payload replay returns the stored receipt, including this field, without a second audit event or intent; payload changes conflict. Replay disclosure is re-authorised.

Supported commands:

- `native.authority.activate`: explicit `mapping_revision`; requires the protected bootstrap capability and current legacy policy revision.
- `access_group.create`: `access_group_id,display_name,description,source_scopes,permissions`; ID is a new UUID and never reused. Each permission has stable `permission_id`, `role_id`, one selectable `action`, explicit `target_scope`, complete `limits` and `separation_of_duties`. Each exact source tuple is explicitly configured on the group and is never inferred from provider claims.
- `access_group.update`: `access_group_id,display_name,description,enabled,source_scopes,permissions`; exact `expected_revisions.access_group` required. Disable retains a tombstone and withdraws only this group's grants.
- `access_group.membership.set`: `access_group_id,principal_id,effective_from,effective_until,enabled`; exact group and authority revisions required. Intervals are UTC `[effective_from,effective_until)`; additions cannot be backdated.
- `ownership.team.create`: `team_id,display_name`; stable new UUID.
- `ownership.team.update`: `team_id,display_name,enabled`; exact `expected_revisions.team` required. Disable retains history.
- `ownership.team.membership.set`: `team_id,principal_id,effective_from,effective_until,enabled`; exact team and ownership revisions required.

Access-group permission actions and limits must be known catalogue values and wholly inside the caller's explicit grantable envelope. Bootstrap capability cannot be granted, removed or escalated by ordinary commands. A separately selectable `ownership.team.manage` action is required for team writes. Owner membership never satisfies any action permission. Existing legacy role/principal commands cannot modify native access memberships or ownership memberships when native mode is active.

Each successful access-group, access membership or activation command commits one `administration.authority.reconcile` intent; team or team-membership commands commit one `administration.ownership.reconcile` intent. Any command affecting both commits both. Intent failure, audit failure or receipt failure rolls back policy state and all records. Authority revisions advance on grants and removals; ownership revision advances independently. Commit paths lock policy first, then re-resolve actor, scope, grantable envelope and object revisions before mutation. A command held behind revocation is denied/conflicted. Group removal withdraws only its grants; account disable or subject-link revocation revokes sessions and blocks new sign-in.

Group removal is a soft disable (`access_group.update` with `enabled:false`) so identity and audit history are retained. The deletion-impact readback is `GET /api/v1/assessment/access-groups/{access_group_id}/deletion-impact`, returning `{schema_version,access_group_id,group_revision,policy_revision,authority_revision,enabled,active_memberships:[{principal_id,effective_from,effective_until}],permission_count,affected_principals,remaining_access_groups_by_principal,withdrawn_actions,expected_intent:{kind:"administration.authority.reconcile",status:"pending"}}`. It is a permission-scoped preview and does not mutate state; the subsequent update command must submit the returned group and authority revisions. The stored command receipt returns the exact intent ID and status. `GET /api/v1/assessment/administration/intents/{intent_id}` returns `{schema_version,intent_id,kind,target_id,authority_revision,status,attempts,last_error,next_attempt_at,completed_at,result,created_at,updated_at}` after rechecking current read/manage scope; `last_error` is always null or the non-sensitive enum `reconciliation_failed`. `result` is null until the worker commits the effect and readback in the same transaction as `status:"complete"`. Authority results are `{effect:"current_authority_readback",authority_mode,authority_revision,policy_revision,target_id,target_present}`. Ownership results are `{effect:"ownership_projection_refresh",ownership_revision,policy_revision,team_id,team_revision,display_name,reporting_input_readback:true,current_group_ids,github_projection_ids,github_projection_readbacks:[{group_id,github_issue_linked,projection_id?,desired_revision?}]}`. For each currently team-owned group with a linked GitHub issue, completion means a desired projection was enqueued and read back; it does not claim an external GitHub send. If effect or readback fails, the intent remains retryable and returns a sanitised failure state. Team-only managers may read their team's intent. The access-group read then shows the disabled tombstone and history; pending intent readback does not claim projection completion.

## Compatibility and reporting

No endpoint infers native authority from provider groups or owner teams. Legacy mode preserves current provider-mapped behavior until explicit activation. Existing owner assignments and issued report/export bytes are immutable. New report calculations record and evaluate native membership event sequence, policy/authority/team revisions, and effective interval boundaries independently at report `as_of` and `known_at`; old reports use frozen inputs. Exports, cursors and receipt disclosure recheck current native authority. No new no-intent exception is introduced.
