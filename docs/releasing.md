## Maintainer preparation and publication controls

The existing workflow is specific to RC1 and must not be rerun to replace it. A future candidate needs a separately reviewed version/workflow change; preserve the published RC1 tag and artifacts. The original RC1 procedure follows for maintenance and recovery reference.

Run the release workflow manually from `main`. It accepts only the clean, exact source revision dispatched from `main`, fails if `v0.1.0-rc.1` already exists, and records the source revision and immutable local Docker image ID. It runs the existing portable checks and must build the image once. All reports, SBOMs, notices, archive content and signatures must identify that same image and source revision. A rebuilt image must never replace the candidate after scanning.

The image inventory contract is `python3 tools/notices/collect.py --image <immutable-image-id> --output <empty-directory>` followed by `python3 tools/notices/verify.py --directory <directory> --image <immutable-image-id>`. Collection must finish with no unresolved license findings. The full Trivy image report is retained; scanner errors, a missing vulnerability database, or fixable High/Critical findings fail the gate. Any exception names the advisory, package and version, rationale, approving maintainer and expiry no more than 30 days away. Broad ignores are not permitted.

Before collection, the workflow runs `tools/notices/prepare_release_sources.py --output <directory>`. It must retain `debian-source-dispositions.json` and its pinned Debian developer keyring; collection receives both explicitly through `--debian-dispositions` and `--debian-developer-keyring`. The workflow also loads the one built image from its saved archive into a fresh local preview using `start --no-build`, then exercises authenticated browser operation, denied peer ingress, restart persistence and owned-resource cleanup before publication can proceed.

RC1 v0.1.0-rc.1 supports fresh installations only. It does not migrate, upgrade or repair historical development volumes. The preview launcher binds the immutable image ID and its revision, version and platform into instance state before creating Docker resources. A resumed partial initialization must use that same binding; an unbound partial state or image change requires destroying that instance and initializing a new one. Established same-image stop/restart remains supported.

The publication job is downstream of the full gates and requires an explicit maintainer dispatch approval. Configure the `volt-rc1-publication` GitHub environment with required human reviewers before enabling any registry or signing command. The publish job alone receives package-write and OIDC-token permissions. Before any registry read, its collision preflight authenticates the GHCR token exchange with the job-scoped `GITHUB_TOKEN` (`GITHUB_ACTOR`/`GH_TOKEN`). Only an authenticated manifest `404` means a tag is absent; authentication denial, permission denial, network failure and other responses stop publication. Credentials are sent only to `ghcr.io`, redirects are refused, and diagnostics do not include the token. The later digest verification uses authenticated access as well. `registry.py --anonymous` is reserved for a separate public-pull check after a maintainer-approved visibility change.

The first successful push creates a private package by default. A package maintainer must separately inspect repository/package access and approve changing the package to Public before anonymous-pull verification; that visibility change is an owner action. The workflow does not change package visibility. After that approval, verify both tags anonymously with `python3 tools/release/registry.py --anonymous --version-tag 0.1.0-rc.1 --sha-tag sha-<full-source-sha> --expected-digest <registry-digest>`; this check proves public pull access and the expected digest, not package ownership or approval. Version and source-SHA tags are treated as write-once: existing tags stop the normal publication path and are never deleted or overwritten. If publication is interrupted after one tag is pushed, do not rebuild. Retain the approved candidate image and its recorded registry digest, have the release owner independently verify the existing tag against that digest, then arrange a reviewed recovery that publishes only the missing tag from that retained image. If the retained digest cannot be proven or the existing tag differs, stop for maintainer disposition. There is no automatic resume path.

GitHub prerelease/tag creation is a separate release-owner handoff. This workflow does not create a Git tag or GitHub Release; neither the dispatch approval nor registry publication implies approval for that action. The owner must separately approve the exact source tag/commit and archive handoff.

The offline archive contains the loadable image, source tar and Git bundle, the maintained `tools/g7_local_preview.py` host launcher, generated notices, both SBOMs, full scan report, provenance, registry digest, signed file manifest, checksums and verification instructions. The launcher is checked against the exact clean source bundle and starts the already-loaded image without rebuilding. Sigstore trust is provisioned independently; a root or checksum carried only inside the archive is never a trust anchor. Corrupt archives, wrong signatures, wrong signer identity, unsigned extra files and mismatched image, scan, notice or registry metadata must be rejected. The same immutable image is scanned and published; publication must not rebuild it. See [launcher-guide.txt](../tools/release/launcher-guide.txt) and [VERIFY.txt](../tools/release/VERIFY.txt).

The offline consumer accepts the OCI layout emitted by the hosted image export when it also carries Docker compatibility metadata. It still verifies the selected platform manifest, image config, labels, every compressed and uncompressed layer digest, and the Docker compatibility manifest. The optional `repositories` map must point the exact imported repository/tag at the final root filesystem diff ID. The only additional OCI blobs admitted are content-addressed legacy per-layer JSON records whose IDs recompute from the selected ordered diff IDs using Moby's `v1.CreateID` and ChainID rules; the parent links must match that same order. Intermediate records use the exporter's zero creation time and container config. The final runtime config must agree with the selected OCI config, allowing only known zero-valued fields omitted by OCI serialization. Unknown members, altered content addresses, foreign IDs, broken chains, contradictory config, additional blobs, or repository/tag disagreement fail closed. See [Moby's tar exporter](https://github.com/moby/moby/blob/v28.5.2/image/tarexport/save.go) and [legacy ID derivation](https://github.com/moby/moby/blob/v28.5.2/image/v1/imagev1.go).
