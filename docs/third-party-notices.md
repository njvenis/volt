# Third-party notices and release inventory

The source repository contains the project license and the reviewed source notices in [`../THIRD-PARTY-NOTICES.md`](../THIRD-PARTY-NOTICES.md). A built image must include a complete, image-specific notice inventory before public redistribution. The checked-in source notice is not a substitute for auditing the resolved image.

## Reproducible image collection

Use an immutable local Docker image ID, not a mutable tag. This collection is limited to `linux/amd64`; it does not run the image. It needs the Docker daemon to inspect and export the image and the reviewed Syft binary pinned in [`../tools/notices/tools.lock`](../tools/notices/tools.lock). Verify the downloaded archive SHA-256 against that file before extracting it.

```sh
python3 tools/notices/prepare_release_sources.py --output /tmp/volt-source-preparation
python3 tools/notices/collect.py --image sha256:<64-hex-image-id> --output /tmp/volt-notices-final --debian-dispositions /tmp/volt-source-preparation/debian-source-dispositions.json --debian-developer-keyring /tmp/volt-source-preparation/debian-developer-keyring.gpg
python3 tools/notices/verify.py --directory /tmp/volt-notices-final --image sha256:<same-64-hex-image-id>
```

`prepare_release_sources.py` creates a new output directory from the reviewed
portable catalog in
[`../tools/notices/debian-source-catalog.json`](../tools/notices/debian-source-catalog.json).
The helper obtains the pinned Debian developer-keyring package from its
catalogued public locator, checks package size and SHA-256, extracts the exact
keyring member, and checks that member against its separate digest pin. It
emits `debian-source-dispositions.json` and
`debian-developer-keyring.gpg` for the following collector invocation. Every
source archive member is checked against the signed `.dsc` SHA-256 and size;
the signed-index verifier also requires unique, complete SHA-256/size rows.
Preparation and final collection outputs are generated evidence; do not commit
them. Use a fresh collector output and verify that exact resulting inventory.

If Debian source-package dispositions have been completed with retained evidence, pass their JSON input using `--debian-dispositions /path/to/debian-dispositions.json`. Relative evidence paths resolve from that JSON file's directory. Each row binds `source_package`, `source_version`, the complete `declaration_resolutions` set (exact SPDX expression and copyright-file SHA-256), and one action: `source-bundle`, `written-offer`, or `excluded`. The collector enumerates each retained DEP-5 `Files` stanza by copyright path and hash, exact stanza hash, and file patterns. Every disposition must contain one matching `file_stanza_resolutions` row per stanza, with the same action and a resolved status; missing or duplicate stanzas remain blocking. A source bundle must include its matching package/version, every source archive member with its exact `filename` and SHA-256, and the `.dsc` path/SHA-256. Maintainer-signed `.dsc` files are checked with `--debian-developer-keyring` (default `/usr/share/keyrings/debian-keyring.pgp`) whose digest must match the reviewed `tools.lock` pin; the archive keyring is a distinct trust root. Where the repository authenticates the complete source set through its signed `InRelease` and exact compressed `Sources` index, the disposition may instead carry `index_authentication` evidence. The verifier checks a pinned archive keyring hash and signer fingerprint, the signed index path/hash/size, exact package/version index row, `.dsc` hash and every source-member checksum. It records this as `signed-repository-index`, never as a maintainer-signed `.dsc`. An offer must include retained text, a SHA-256, scope and validity; if it has an expiry date, an expired offer fails. An exclusion must resolve every declared expression to one complete SPDX term and include exact covered-file-pattern evidence plus reviewed source-file SHA-256. For `A OR B`, one complete branch may be selected; for `A AND B`, every conjunct must be accounted for. Missing, stale, partial, or malformed rows remain blocking. The verifier checks the copied output evidence and package/version identity; `action_choices` are not completed dispositions.

The output includes `sbom.syft.json`, `sbom.spdx.json`, a Syft SBOM for the digest-pinned Valkey source image, `notices/`, and `notice-manifest.json`. The manifest binds the inventory to the immutable final image ID and platform and records SHA-256 for every emitted artifact, source input and Syft binary. The pinned registry manifest digest and the daemon's local image/config ID are separate identities: the collector resolves the full pinned reference, requests `linux/amd64` when pulling, checks the exact repository digest and platform, and uses the returned local ID for Syft and export. The verifier checks that admission record against the retained Dockerfile and source SBOM. Keep the raw outputs with the release evidence. The verifier parses both SBOMs, checks image/manifest bindings and joins complete package identity/version/purl/location evidence to captured license texts or exact dispositions. It treats Syft `NOASSERTION`, missing package identity and unmatched inventory rows as findings. The UI production lock's resolved tarballs are checked against npm SHA-512 integrity; checked-in license assets are independently matched to package versions/integrity and the lock's production package set. The collector also hashes the project notices and every curated `third-party/notices/` asset from the exported image and compares them with the checked-in bytes. The actual bytes of each copied Valkey/musl/OpenSSL runtime binary are compared with the corresponding path in the explicitly admitted source image, following symlinks. Export containers are removed with their anonymous volumes on success or failure, and exact container/volume IDs and cleanup exits are recorded. Collection returns nonzero when required notice/source evidence is missing or ambiguous. Verification returns nonzero for incomplete or modified output or any unresolved finding.

The collector records exact package license expressions as discovery evidence and preserves `AND`/`OR` structure. Debian license detections are attributed to their retained copyright file and grouped by Debian source package/version; individual license-name occurrences are not counted as independent source-offer obligations. `notices/debian-source-packages.json` supplies exact source names/versions, affected binary package versions and copyright file digests. Every candidate in `notices/debian-source-candidates.json` stays release-blocking until a complete, fresh, evidence-backed disposition is supplied; the candidate/action list itself does not clear an obligation. Vendored Windows PE launchers are separately classified and digest-bound to exact distribution evidence. Setuptools launchers are matched to the pinned wheel and all image PE members. pip 26.2.1 launchers are matched to the published wheel checksum, installed `vendor.txt`, all six wheel PE member hashes and the exact bundled wheel license text at `notices/PIP-26.2.1-DISTLIB-LICENSE.txt`. The downloaded wheel and installed launcher target are checked independently; missing, extra or changed PE files block collection. The final offline verifier also replays the retained wheel members against captured target bytes and disposition records. Python licence declarations in METADATA do not substitute for licence text: texts must join the exact installed distribution, or an independently checked versioned disposition. The collector retains hyphenated and suffixed names such as `LICENSE-APACHE`, `COPYING-MIT` and `mit.LICENSE`. For packageurl-python 0.17.6 and titlecase 2.4.1, whose installed distributions omit their upstream texts, the full MIT grants and copyright notices are pinned in `third-party/notices/PYTHON-SUPPLEMENTAL-LICENSES.json`, embedded with the other notice assets and replayed against retained exact-version source archives. `notices/package-license-dispositions.json` contains evidence-backed package dispositions with content hashes, exact license text, copyright, source material and provenance; missing or ambiguous metadata remains unresolved. The copied musl libraries require the complete versioned `COPYRIGHT` notice, checked against the recorded tagged source and Alpine package metadata. Do not treat the UI-only source tree assets or the baseline image report as final release clearance.

## Current limitation

The release inventory is intentionally fail-closed. Until the final image has been collected, all applicable license texts and copyright attributions have been reviewed, source offer obligations have been assessed, and `verify.py` passes for that exact image ID, image redistribution remains blocked. Do not describe a local SBOM or a source-tree notice as completed image license review.
