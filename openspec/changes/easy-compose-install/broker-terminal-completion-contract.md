## Authority and unchanged durable wire

The ORIGINAL root broker named by launch.json.supervisor is the ONLY writer of launch.json, launch-status.json and supervisor.json for that launch, including starting/ready/quiescing/failed/stopping/stopped. Its authority does not transfer. PID1, readiness/control helpers and orphan cleanup lose these publication calls. Root role alone is insufficient: each Store publication checks EUID0, os.getpid() == original broker.pid, current process proc_start_ticks == original broker.proc_start_ticks, actual PPID == original entrypoint.pid and the original entrypoint identity is live. The current launch record and all identity joins are read under the shared lock. Initial publish_launch checks the proposed live chain before publication. API-dead terminal publication checks the broker/entrypoint, not an impossible live-API predicate.

launch.json retains its EXACT existing closed fieldset/profile. launch-status.json retains its EXACT existing fieldset/profile, with ONE explicit private enum extension: phase=api_stopped permits result=none|api_nonzero|forced_stop|cleanup_failed. This is a broker-reaped API progress milestone, NOT terminal success; no new field/file. No missing field defaults, backfill, reconstructed status, disk poison bit or extra route-store inventory. Shared custody, immutable lock inode, no-follow bounded reads, rename/fsync ordering, closing barrier, proc_dead and cleanup-only partial-supervisor rules remain unchanged. No public field or grant.

A root caller cannot create an old launch's terminal outcome by matching JSON identities. publish_launch_status(value) and publish_supervisor(value) enforce the original broker process check. publish_launch(value) cannot reset SAME-launch status or failure. A genuinely DIFFERENT launch may retire old records ONLY under the existing proved-dead old API AND old broker, disarmed/no-observations/no-temp custody guard; it cannot adopt old clean authority. A new PID with reused numeric PID fails proc_start_ticks. Existing unsafe/mixed metadata fails closed.

### Exit observation/request ordering

The original broker session starts with controlled_request_registered=false. Only an actually admitted ordinary-stop or quiesce event for its registered launch can set it; no helper/status read, terminal frame or subsequent TERM may retroactively register an already observed exit. Before registering a first request, the broker checks retained API pidfd/waitpid(WNOHANG); if exit has already been observed, process it as unrequested first. In its serialized event loop it then registers the request BEFORE signalling/processing further exit events. If readiness/exit and request arrive together, already-observed/readable exit is processed first, fail closed. This is an observation ordering rule, not an unsupported claim of exact kernel exit timestamps. A late exit0 after a previously registered genuine quiesce request is eligible even after that quiesce timed out, provided no other latch was set. KILL/nonzero/publication failure remains dirty. unexpected_api_exit is a new finite PRIVATE session reason only; launch/status fieldsets and durable result enum remain unchanged. API-progress may still permit necessary cleanup, but no clean seal/positive completion follows unexpected_api_exit.

## PID1 ordering and sticky state

PID1 has an irreversible in-memory failure latch set BEFORE any fallible reporting on service cleanup failure, forced termination, critical-child loss, publication uncertainty or invalid completion protocol. A genuine no-kill quiesce timeout ALONE is recoverable; a reporting/publication failure during that timeout is not. Neither process clears its latch within this launch.

Ordinary stop ordering:

1. PID1 retains original broker PID/proc_start_ticks/direct-child registration and sends ordinary TERM. Broker clears readiness, stops/reaps its actual API and durably closes/disarms route observations; it remains alive. PID1 polls the exact launch/API identity and disarmed state only as an intermediate progress milestone, never as terminal success.
2. PID1 proceeds with ALL required workers, databases and other launch-affecting cleanup WITHOUT first waiting for broker exit. Existing shutdown steps after broker reap must move before terminal handoff. API stop grace remains 30s, forced reap 2s, route cleanup 2s; do not turn proxy availability into a stop prerequisite.
3. PID1 finalizes its service wait results, required cleanup publications and open failure-producing teardown. It authorizes exactly one terminal frame and transports it through the single registered protected adapter, requiring actual adapter reap0 as specified below. Success means every such step is DONE, no launch-affecting cleanup remains, and its latch is clear. Failure means cleanup was attempted but clean eligibility is lost. There is no later success frame after failure.
4. After PID1 has successfully reaped the adapter, it may wait for the broker. Independently, broker receives/validates the frame with no Store lock held, checks its own independent latch/reap/disarm, publishes terminal candidate with fsync ACKs and exits zero only on complete success; it retains the exact canonical final launch-status bytes it acknowledged, and no subsequent status rewrite is allowed. PID1 reaps that EXACT direct broker child and checks normal exit0. Broker death/timeout/nonzero never permits a replacement writer or synthesized success.
5. PID1 emits the existing PRIVATE Docker-log kernel-completion envelope specified below and exits0 only after its own latch remains clear and the bounded producer reports success. This acknowledgment and exit are protocol finalization, not deferred service cleanup. Any failure during finalization means nonzero/no completion acceptance. No EXIT trap may silently replace that result with zero.

Quiesce timeout keeps BOTH PID1 and broker alive supervising the same API, no ready/backup. A later ordinary TERM can complete cleanly ONLY if neither has suffered a publication/lifecycle failure. No timer after a no-kill timeout may silently initiate ordinary termination.

Entropy failure latches failure. One frame for one launch's one final ordinary stop; quiesce timeout sends NO frame and does not close the channel. PID1 delegates that already-decided complete frame exactly once to the protected adapter below. ## Finite state and crash matrix

Broker normal status progression remains running -> quiescing -> quiesce_failed (recoverable timeout), or stopping -> api_stopped -> stopped/clean_stop ONLY after the terminal success gate.
