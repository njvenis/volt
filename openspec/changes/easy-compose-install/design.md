## 1. Persistent identity and sessions

Add supported local accounts, separate from OIDC links and the synthetic provider. Persist an immutable installation UUID/authentication mode; additive migrations must not infer local mode from an empty session or silently convert an existing database. Local startup against established incompatible identities/authority fails closed. Legacy external/demo behaviour and provider-cap intersection remain unchanged.

Use the already pinned cryptography Argon2id PHC API with random 16-byte salts, 32-byte output, 19,456 KiB memory, two iterations and one lane. Confirm the actual packaged implementation; never fall back to weaker hashing. Passwords are NFC-normalised, 15–128 code points, with no trimming/case changes/composition rules; allow paste/password managers and reject a versioned local common-password list. No remote password lookup or claimed certification. References: https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html and https://pages.nist.gov/800-63-4/sp800-63b.html .

Use unique case-insensitive ASCII usernames [A-Za-z0-9][A-Za-z0-9._@-]{0,63}; display names are separate. Do not link identities by email/name. Add account, local-session, persisted throttle, installation-mode, setup-claim and recovery records in UVM PostgreSQL, with stable UUIDs, credential revisions and explicit UTC timestamps. Store only token digests and PHC verifiers, never passwords or capability values.

Local sessions have random 32-byte opaque tokens, HttpOnly/SameSite=Lax cookies, CSRF binding, one-hour absolute expiry and persisted revocation. Secure cookies are required for HTTPS; HTTP is limited to the exact configured loopback origin. Recheck session/account/principal/credential revision and current native grants on every request; recheck write authority under the existing policy lock. A local session is not bootstrap authority. Local mode disables fixture bearer and synthetic provider paths.

Persist generic-error throttles across restart: five attempts per username and 30 per trusted peer per rolling 15 minutes, with Retry-After. Unknown accounts use comparable dummy verification. Bound concurrent expensive hashing; document the real packaged worker/process limit. Do not trust arbitrary forwarded headers.

Password change requires current password and CSRF, increments credential revision and revokes all sessions including the caller. Disable and recovery also revoke sessions. Host-authorised maintenance issues private, 15-minute single-use recovery/enrolment capabilities; browser completion consumes them atomically with verifier/revision/audit changes. Recovery cannot create accounts or grant roles. Additional accounts use a host-created pending account, never public self-registration. The host maintenance command atomically creates the principal and pending local account with no verifier, no native membership and no bootstrap authority, then issues a private enrolment capability. POST /api/v1/auth/local/enrol accepts that capability and a new password; it atomically installs the verifier, activates only that pending account, consumes the enrolment and appends audit/receipt. It returns 204 and requires normal sign-in. It cannot rename/link another identity or assign authority. Recovery applies only to established enabled accounts and cannot activate pending/disabled accounts. No public registration/email reset is introduced.

All setup, enrolment and recovery capabilities are explicitly purpose-separated and bound to installation UUID, target account (or the unclaimed installation for setup), generation and current credential revision where applicable. Hash a domain-separated encoding of those bindings plus a random 32-byte secret, compare in constant time, and validate the persisted bindings rather than trusting token assertions. A non-secret record identifier may locate a token; it does not authorise an operation. Endpoints reject cross-purpose/account/installation/generation use. Reissue invalidates the previous generation; credential change/disable revokes outstanding account enrolment/recovery capabilities as well as sessions.

## 2. Protected browser first administrator

Generate a 32-byte random capability in a mode-0600 private file below the mode-0700 owned instance directory. Register its digest once in PostgreSQL, expiring 30 minutes after registration. Database consumption/generation dominates retained files: restart, restore or a stale file must never reopen setup. Host-authorised rotation is explicit and allowed only before established account/bootstrap authority; it invalidates the old generation.

Interactive setup displays URL and capability directly to the controlling terminal, not ordinary stdout/stderr logs. Do not put secrets in URLs/fragments, argv, environment, receipts, audit payloads, diagnostics or browser telemetry. Unattended setup prints only the private delivery path; an explicit protected show command is available. No user copies a session cookie or internal identity ID.

Claim input contains capability, username, display name and password only. It requires no scanner/source identifiers. Acquire the existing policy lock, policy row, claim row and account/principal/session rows in that order. Recheck mode, installation, token digest/generation/expiry, username uniqueness and absence of established authority under locks. Create account/principal, protected bootstrap administrator set, native authority, session, capability consumption, audit, receipt and reconciliation intent in one transaction using shared validated services. Do not call HTTP handlers or nested independent transactions. Set the browser cookie only after commit. Audit/receipt/intent failure rolls back every change. Real PostgreSQL races must produce exactly one administrator; replay is denied; a lost success response is recovered by ordinary login.

A claimed administrator reaches an honest empty deployment dashboard. It must not query forbidden source data and turn permission errors into empty results.

## 3. Supported scanner onboarding

Add protected deployment capabilities deployment.read and connector.binding.register, checked against the persisted protected administrator set, not an arbitrary authenticated session. Registration uses the existing command/receipt transaction contract, CSRF, current revisions, rationale and evidence. It allocates stable IDs and persists a unique supported source binding, initially disabled/unverified. It performs no network contact.

Under policy-first locking, registration atomically stores the binding and registry revision, extends only that exact local source envelope, creates a configurable native connector-administration group/membership and grants connector.read/configure/secret.manage for that connector and exact tuple. The onboarding UI explicitly grants read access to imported findings/audit for that same source by default, making the choice visible and configurable; it grants no assessment-write, exception approval or remediation-confirmation power. All later authority follows native grants and separation of duties. No global wildcard/demo scope is fabricated.

Normal browser registration, not a host-only amendment, supports later scanners. Preserve OIDC's independently configured ceilings; this local-only registration path does not expand external provider authority. Existing configured bindings for external/demo paths remain compatible. Local mode uses persisted supported bindings rather than fixture environment variables.

Expose the existing configuration/secret/validation/activation workflow after registration. These remain separate permission-checked operations. An instance-local encrypted secret key/binding is generated privately and backed up; the browser receives binding IDs, never paths/key bytes. No activation occurs merely because registration or login succeeded.

### Initial grantable ceiling and effective grants

For the new local contract only, persist native contract version 2. Its grantable action list is exactly policy.read, access_group.read, ownership.team.read, ownership.team.manage, connector.read, connector.configure, connector.secret.manage, assessment.read and audit.read. Do not store an action wildcard. This is a conservative onboarding ceiling, not an effective grant or a promise that every assessment/approval action is enabled. Broader workflow policy remains explicit owner-authorised configuration under the existing validated policy boundary; the installer never fabricates that authority.

The legacy finding target_scope ceiling starts with group_ids/source_families/environments/service_ids all empty and membership_mode explicit. source_scopes starts empty. Add local-only typed target ceilings: deployment_targets contains only this installation UUID; connector_targets is an empty list of exact connector-UUID/source-tuple pairs; source_read_targets is empty. An empty source ceiling grants no source authority. Existing v1/OIDC/demo selector validation is unchanged.

The complete limits document has maximum_acceptance_days and maximum_severity null; whole_group_confirmation false; allowed_environments, allowed_service_ids, allowed_sla_clock_bases, allowed_sla_severities, allowed_sla_start_sources and allowed_identity_scalar_fields empty; maximum_sla_duration_seconds and maximum_deadline_extension_seconds null; allow_sla_backfill false. These limits do not grant any action. Approval/remediation/SLA actions are absent from the initial action ceiling. Separation-of-duties is approval_requires_distinct_actor true, prohibit_requester_approval true, required_approver_count 1 and prohibited_action_pairs empty, retaining existing fail-safe schema defaults without claiming an organisation's policy.

Initial effective native membership is one generated installation-administration group for the claimed principal, with only policy.read, access_group.read and ownership.team.read targeted at this exact installation. Protected bootstrap membership remains separate and authorises only its defined administrative operations. No source, connector, finding write, approval or remediation grant exists at claim time.

The current finding-selector language cannot represent an exact connector before findings exist without dummy selectors. Add only these explicit local-v2 target variants:

| target_scope kind | Shape and restrictions |
| --- | --- |
| deployment | deployment_ids is a non-empty exact UUID list within deployment_targets; only the named administrative read/team actions are allowed; the access group has no source scope |
| connector | connector_ids is a non-empty exact UUID list; only connector.read/configure/secret.manage; every ID/source pair must match connector_targets and the persisted binding |
| source_read | membership_mode all_current; only assessment.read/audit.read; access-group source_scopes must be a non-empty subset of source_read_targets |

Keep legacy finding-target validation unchanged; do not insert a connector UUID as a fake finding-group ID, invent service/environment IDs or add wildcard selectors. Typed target and action must agree. Deployment groups with empty source scopes are allowed only when every permission is a valid exact deployment target; they cannot become a global source grant.

Registration adds only the one allocated connector/source pair to connector_targets, its exact source tuple to source_scopes, and (if explicit grant_initial_read is selected) the same tuple to source_read_targets. It does not change the action ceiling, limits, duties, legacy selectors or any unrelated source/connector. The new connector group receives only its three exact connector permissions; optional read permissions use source_read. Both membership and ceiling/grant delta are in the same audited command receipt/transaction. Pair validation prevents cross-combining connector A with source B.

Source-read authorisation resolves current observed groups/members within the exact registered tuple; it never turns empty finding selectors into a global wildcard. No observations means an authorised empty result, not fabricated findings. Other finding/approval scopes keep their existing explicit validation. These typed scopes make normal exact delegation possible after registration without broadening external OIDC ceilings.

## 4. Browser and runtime interfaces

The authoritative interface is docs/easy-install-api-contract.md. New responses are schema-versioned and no-store. Validate exact Origin and JSON for unauthenticated credential operations; authenticated writes additionally require existing CSRF. Safe errors never echo input secrets or raw validation bodies. Extend shared credential modes with local_session, preserving existing OIDC/GitHub paths.

Frontend states cover loading, setup, expired/invalid/consumed capability, submitting, throttled, unavailable, signed out, empty dashboard, scanner registration, permission denial and password/recovery completion. Secrets live only in component memory and are cleared on submission/navigation. Use existing VOLT assets/tokens, light theme and accessible keyboard/error/focus/reflow behaviour. Never retain request bodies, secrets, HAR or unredacted form DOM in test evidence.

Local runtime configuration binds installation UUID, exact public origin, secret-source identity and file paths. UVM_AUTH_MODE=local is explicit; legacy absence preserves existing OIDC/deployment-mode behaviour. Local mode never starts the synthetic provider or Okta publisher. Delivery/backend agree and record the exact config schema before coding dependent interfaces. API readiness distinguishes awaiting administrator from ready; an unclaimed instance does not claim usable configured authority.

## 5. Independent small-package trust

The [independent verifier amendment](bootstrap-amendment.md) supersedes the original Cosign-only image choice below. It retains signatures/provenance and complete pre-execution graph admission, and explicitly authorises the owned positive transparency fixture. It does not relax any authentication or extraction gate.

A future versioned small package contains the host launcher, its Sigstore verification bundle, signed online descriptor, signed Compose bundle and ordinary instructions. It contains no offline image archive. The expected release, exact main-only release-workflow identity, OIDC issuer and independent verifier OCI index digest come from a trusted project/release page or managed provisioning, never the downloaded package. The verifier contains pinned Cosign and graph/archive policy. RC4 keeps the existing main-only protected publication convention; do not invent a refs/tags identity incompatible with that gate.

The single copyable setup command runs the independently pinned minimal verification image with read-only package mount, dropped capabilities, no-new-privileges and narrowly writable ephemeral cache. It includes pinned Cosign and independent graph/archive parsing policy, authenticates the launcher before sh invocation and completes graph admission before application helpers execute. Commands are sequential and propagate failure; no curl-pipe-shell, eval, self-checksum trust or unchecked candidate execution. The user already downloads/extracts the small package, so an additional fetcher image is unnecessary for the default route. Docker fetches the verifier image by its independently trusted digest. Disclose this image's transfer size separately. Ordinary POSIX utilities are allowed and documented; no host application build tools are required.

The authenticated launcher fixes its release/source, verifier, descriptor digest and runtime index. It rejects an externally selected release mismatch. The signed descriptor binds bundle hash/size, source snapshot, platform children, installer/runtime contracts, schema head and provenance subject/type/digest. Avoid circular launcher/descriptor hashes. Authenticate all package data before extraction and enforce closed inventory, bounded regular-file extraction and link/traversal/duplicate rejection. Verify index signature/provenance and the index-child/source graph, then pull the daemon's supported architecture by immutable index. Preserve registry/index, platform-manifest, local index and config IDs as distinct identities.

Only after complete signature, provenance, source, index/child and archive graph admission may a helper inside that immutable runtime run Python/OpenSSL work. It receives narrow instance/bundle mounts, never the Docker socket or a broad host/home mount. Host sh owns fixed Docker/Compose commands; helpers exchange versioned data/files, never executable shell. Validate effective Compose configuration and every owned resource before actions.

Production verification fixes exact signer identity/issuer and transparency/provenance policy. No wildcard issuer, insecure skip flag, mutable tag or fixture trust is accepted by production setup. Existing offline archive installation remains advanced and old versions/assets are unchanged. There is no public RC4 package yet; generated trusted commands must contain real pinned values and be tested before documentation presents them as usable.

## 6. Instance lifecycle and host support

Persist installer contract version 2: stable installation/project/owner IDs, immutable auth mode, paths, release/source/bundle/helper/runtime/platform identities, origin/binds, schema compatibility and phase. Phases are verified, prepared, resources-created, started, awaiting-admin and ready. Use exclusive locking and atomic durable journal updates. Resume validates identity, committed files and resource ownership; preserve established secrets, fail on contradictory/missing committed state and never adopt foreign resources. Handle killed/interrupted work explicitly, including stale locks; no silent overwrite.

Preflight Docker/Compose, daemon/context, daemon architecture, ports, private-file permissions and relevant resources. Record measured test resources and distinguish guardrails from measured minimum requirements. Support paths with spaces and validate effective Desktop bind permissions. Do not source .env as shell code. Reject unsafe path/mount syntax with actionable errors; test dollar quoting. Do not require host ip or host-network privileges: Docker allocates an owned bridge from its pools, effective network/peer identities are recorded and validated, conflicts fail visibly, and explicit subnet overrides are validated. Do not silently widen trusted peers.

Default application and recovery access is loopback. Server mode requires an explicit HTTPS origin, hostname, bind and certificate/key configuration, with validated ingress and no exposed synthetic identity provider. Keep the supervised image; do not decompose services. Local engine and Docker Desktop interfaces are supported structurally, but actual macOS/WSL qualification is unverified until exercised. Remote-daemon host-bind contexts fail explicitly. WSL Linux filesystem is recommended; any selected path must satisfy the same effective privacy check.

Expose practical setup/resume, start, stop, status, logs, diagnostics, account maintenance and cold backup/restore commands, with exact tested names in docs. Stop/ordinary removal preserves data. Destruction is separately explicit and owner-confirmed. Diagnostics redact secrets and request bodies.

Reuse cold-stop safety, all-three-store inventories, restore fences and existing same-path/project/image restrictions. Back up accounts, authority, credential/claim/recovery state and encryption keys with private configuration. Restored consumed claims remain consumed. Before local-mode ingress opens after restore, an audited recovery-generation transition revokes restored sessions and all outstanding enrolment/recovery capabilities; legacy OIDC/demo recovery semantics are preserved. Unclaimed restored instances require explicit token rotation. Keep scanner credential quarantine/external-effect reconciliation limits honest. No unqualified pull-latest upgrade: unsupported image/schema transitions and downgrades fail; image rollback is not schema rollback.

The [local recovery profile amendment](local-recovery-profile.md) supplies the previously missing supported Qualys clearance producer/application path. It is explicit local-only authority with separate runtime issuer and host-only operator keys, semantic password-reuse rejection and audited epoch-bound application/test/activation. Existing fixture authorities are not relabelled as supported external issuance.

## 7. Verification and publication boundary

Adapt the maintained Compose qualification and browser companions, rather than replacing them with a mock-only harness. Run the actual small package outside checkout with a minimal host PATH, real PostgreSQL and runtime. Use an owned loopback registry and independently provisioned test signing key/policy to sign launcher, descriptor, bundle, runtime and provenance. No skip flag or candidate-supplied test key. Production rendering rejects fixture policy. This proves packaged admission, not release-time Sigstore/GHCR publication.

Test native Linux AMD64 locally and native AMD64/ARM64 in read-only unmerged-PR CI, transferring OCI artifacts/local registries without public image pushes, emulation or release dispatch. Record all source/image/tool/config/fixture identities, commands, output, exits and owned cleanup. Include actual PostgreSQL claim races and audit/receipt/intent rollback, browser setup/dashboard/scanner configuration, permission removal, password/recovery/throttle/restart, resume/secret preservation, wrong trust/index/ports/registry/resources, cold restore and auth state, default loopback/HTTPS negatives and upgrade rejection. Preserve existing OIDC/demo tests. Independently review fixed source and executed evidence. Human visual, live scanner/IdP, Desktop and production claims remain separate.
