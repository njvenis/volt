# Supported local scanner recovery profile

## Evidence, authority and scope

Bridge review6b found no usable route out of restored Qualys quarantine. The backend owner confirmed that existing schema1 issuer/operator documents are fixture authorities, with no supported producer/application operation. Its executable verifier uses Ed25519 despite an obsolete HMAC description. Reusing manually edited ledgers or treating fixture signatures as production authority would not meet this task.

The primary adopts **volt_local_recovery_v1**, only for explicitly configured new local-account installations and registered Qualys VM sources. This uses the user's authority to choose a practical local installation/recovery design. It preserves quarantine, current native grants, restore epoch, fresh credentials, independent host approval and audited activation. It does not change existing external/demo schema1 behavior, silently migrate modes or claim external/vendor credential issuance, independent human approvers, production/G7 qualification or live Qualys acceptance.

## Separate authority and key custody

The encrypted-local service is the credential issuer for this profile: it attests a server-validated fresh local credential version, not vendor identity or vendor password-rotation evidence. A separate host authority approves that exact attestation. The authenticated application session remains necessary for the subsequent browser transition; neither signature supplies an implicit application grant.

At new-instance preparation, the admitted helper generates once: an Ed25519 issuer signing key, a DISTINCT Ed25519 host-operator signing key, and a separate random32-byte material-binding key. Do not reuse the AES storage key, either signing key, or password hashes as this binding key. Preserve established keys on resume; missing or contradictory committed material fails closed. No implicit key replacement/rotation is provided. Backup and restore include all keys and public configuration under protected coordinated inventory; key-loss recovery is not a silent re-enrolment shortcut.

The API runtime receives its issuer/material keys and PUBLIC operator trust root. The operator PRIVATE key remains in a host-owned authority directory outside EVERY runtime/API mount, including ancestor mounts. An admitted ephemeral signing helper may read it through a narrow read-only mount, with no network, socket, extra privileges or broad home mount. Actual resolved Compose/inspection admission must enforce this exclusion. Distinct public keys and installation/key IDs are validated. The backup wrapper can access host authority during an explicit owned cold backup; the API must not serve or mount that private backup material.

Use trusted server configuration `/etc/volt/local-recovery.json`, selected through UVM_LOCAL_RECOVERY_CONFIG_FILE, with schema_version1/profile, installation_id, issuer_key_id/operator_key_id, public-key paths, issuer-private/material-key paths and private proof-store settings. All paths are server/installer configuration, never browser arguments. The operator private path is NOT API configuration. Exact field spellings and maintenance JSON schemas must be pinned by the owners before dependent implementation. Unsupported/missing local profile fails recovery closed; local mode must not fall back to fixture/schema1 proof validation.

## Exact fresh-material rule

Only a recovery upload in quarantine can create a recovery attestation. Under the existing policy/connector/allocated-slot locks, decrypt and parse **all retained Basic credentials for that connector/slot/purpose, including revoked versions**, through existing crypto. Reject reuse of any retained password even when username, JSON whitespace or key order differs. Compare the parsed external password without trimming, case conversion or changing the credential supplied to Qualys. Use constant-time equal-length private keyed comparisons; do not expose comparison tags, matched indexes, plaintext hashes or credential values through browser/audit/logs. Undecryptable or malformed retained material fails closed. A new ID, ciphertext, nonce or client freshness flag is not sufficient.

An exact replay first follows the existing terminal submission/version contract; it must not compare a committed version against itself and invent a new upload. A novel version must pass the freshness rule before its encrypted value, issuance attestation and audit commit together. Failed freshness/attestation/audit leaves no active new version. New recovery uploads do not clear quarantine or activate a scanner. Ordinary clear-state credential updates preserve existing behavior and do not require host approval; all retained versions remain available for a later recovery comparison.

For equal-length private comparisons, HMAC-SHA256 input is the byte prefix `VOLT.local-recovery.password-equality.v1\0` followed by the declared canonical JSON of installation_id,connector_id,secret_id,purpose,password. Username, version and epoch are deliberately absent from equality comparison. Compute all retained tags through the same private key and compare without exposing them. Credential commitment instead uses prefix `VOLT.local-recovery.credential.v1\0` followed by canonical JSON of profile,installation_id,connector_id,source_id,source_tuple,secret_id,version_id,purpose,recovery_epoch_id and credential={username,password}. It binds the entire accepted credential/context while equality cannot be bypassed by a new ID or username. Prefix terminator is a zero byte, not two literal backslash characters. Persisted/serialized commitments use lowercase64-hex; proof signatures use the encoding below.

## Proof encoding and binding

Use existing Ed25519 encoding: raw32-byte public keys; strict standard-Base64 64-byte signatures; signed bytes are Python `json.dumps(document_without_signature, sort_keys=True, separators=(",", ":")).encode("utf-8")`, with default ASCII escaping and no added newline. This is the declared Python encoding, not an RFC8785 claim. Reject duplicate JSON keys, unsupported types/versions/profiles and unknown fields in the new closed schemas. Key IDs and roles are fixed by trusted configuration, never selected from the payload to load arbitrary keys.

Recovery issuer attestation is one schema_version2/profile=volt_local_recovery_v1/document_type=credential_attestation object. Required signed fields: attestation_id, installation_id, issuer_key_id, connector_id, source_id, exact source_tuple, secret_id, version_id, purpose=qualys_vm_basic, recovery_epoch_id, issued_at, issued_after_epoch=true, freshness_policy=no_retained_password_reuse_v1 and credential_commitment. The commitment is HMAC-SHA256 under the separate material key over a domain-separated encoding binding all those identities/current epoch and canonical parsed username/password. It is private proof data, not a reusable public password hash. The backend validates the committed material binding and current version on every recovery use.

Host approval is schema_version2/profile=volt_local_recovery_v1/document_type=operator_clearance. Required signed fields: approval_id, installation_id, operator_key_id/operator_id, connector_id, source_id, exact source_tuple, secret_id, version_id, purpose, configuration_revision, recovery_epoch_id, attestation_sha256, rationale, evidence_ref, issued_at and expires_at. The digest is SHA256 of the complete canonical signed attestation INCLUDING its signature. Operator identity must match the configured host authority. Validity is at most15 minutes, with explicit UTC timestamps and no future issuance. No version lists/wildcards or caller-provided trust roots.

Proof consumption validates EVERY binding against current persisted state and the independent host restore epoch. The issuer and operator keys must differ. Wrong purpose/profile/schema/installation/source/slot/version/configuration/epoch/attestation/key/signature/time fails closed. An exact idempotent import/apply returns its committed acknowledgement; altered proof/reused IDs conflict.

Issuer issuance time must be within the current epoch and not in the future; it has no arbitrary client-supplied validity. A current fresh version can receive a new explicit short-lived host approval later in that same epoch, subject to every current fence. This does not allow another upload of old material or renew an approval automatically.

## Supported host producer and browser application

The proposed user entry point is `sh ./volt recovery approve-scanner`, with the existing instance-directory selector, a human source selection (or an unambiguous label), rationale and evidence reference. Delivery must implement and test the exact flags before ordinary docs present a runnable command. Never emit an executable shell command containing unescaped labels; no internal ID, proof file, signing key or cookie is manually copied.

The wrapper validates the owned admitted instance and current restore journal. It invokes fixed backend maintenance services inside the owned runtime to produce a current signed request/attestation plus SAFE target/configuration/epoch metadata. Private host temporary files use0700/0600. An admitted ephemeral helper, running without network, verifies the issuer proof against the independently stored public root and journal, signs using the host-only operator key, and returns a versioned approval. The wrapper streams it over stdin to a fixed backend import operation inside the owned runtime. No private key, credential, proof value or cookie appears in argv/environment/ordinary logs. Backend validates then stores/audits the approval; it does not receive the operator signing key. No manual SQL or arbitrary maintenance shell/data execution is offered.

The host command creates approval only; it does NOT clear quarantine, test, collect or activate. The user returns to the normal browser session and explicitly applies it via `connector.recovery.clearance.apply` on the existing shared command endpoint. Use the established connector command envelope/target and complete revision vector; owners must publish its exact wire JSON before the UI implements it. Payload is exactly connector_id,source_id,secret_id,version_id,recovery_epoch_id,rationale,evidence_ref. Require current exact connector.configure, Origin/JSON/CSRF and validated matching host approval. Bootstrap status alone confers no bypass.

Under policy-first locks, application atomically writes audit/intent/receipt, consumes the approval into this exact recovery workflow, advances connector revision once and moves quarantined→awaiting_activation. Keep the scanner disabled, active configuration null and requires_fresh_credentials=true. Replay of the same currently authorised command returns its receipt; another command cannot reuse its approval. Receipt/intent/audit failure rolls back the whole transition.

An expired or invalidated approval may be replaced only by a NEW explicit host action for the current configuration/version/epoch. Import atomically supersedes the old approval, disables/invalidates any pending test and returns to a closed quarantine workflow; it never activates anything. Preserve append-only provenance. Credential/configuration/epoch changes invalidate prior approvals and tests; no automatic renewal or fallback.

## Test, activation and normal operation

While awaiting_activation, only an explicit bounded connection TEST may lease the exact fresh credential, after current issuer/operator/epoch/session/grant checks. No collection or publication is allowed. Release the database/policy lock before network. A successful test proves API access only; it does not prove vendor account identity or complete coverage.

Activation requires the same current approval/configuration/version/epoch and an exact successful test within15 minutes. One current-authorised transaction clears quarantine, sets requires_fresh_credentials=false, activates that configuration and writes audit/intent/receipt plus the truthful approval provenance. Any failure leaves it closed. Current operator-proof expiry is checked through activation; AFTER successful clearing, ordinary operations use the committed activation/current credential/epoch fences, not an approval expiry that would disable a scanner fifteen minutes later. Another restore quarantines again under a new epoch.

Expose safe recovery readback with state, epoch_id, fresh_credentials_required, fresh_version_ready, clearance_state, approval_id and approval_expires_at. It contains no credential/digest/proof/key/path data. UI distinguishes upload→host approval→apply→test→activate; it must not substitute an error for success or ask for developer tools. Exact nested names become the provider/backend checkpoint before UI changes.
