## Kernel exec channel and ordering

Broker creates one error pipe `pipe2(O_CLOEXEC)` and opens exact ELF FD BEFORE fork, validates owner/ancestors/stat/magic. Error pipe is NOT a success-message pipe and is never stdout/log. Before fork broker is single-threaded, explicitly uses SIGCHLD=SIG_DFL (never SIG_IGN/SA_NOCLDWAIT), blocks SIGCHLD, and has NO async reaper or other wait/waitpid caller. Root child first blocks on a NEW private CLOEXEC one-byte exec-GATE pipe while still executing fixed protected code; only b"G" proceeds, EOF/invalid/2s timeout exits70 without executing API. Parent calls pidfd_open IMMEDIATELY after fork BEFORE unblocking SIGCHLD, before ANY wait/reap and before sending G. Even an early child exit remains its unreaped zombie, so PID cannot recycle during pidfd_open. Parent retains pidfd+original PID/startticks, then sends G exactly once. On pidfd_open failure parent closes gate (child exits), closes error channel, reaps its STILL-UNREAPED OWN child by waitpid and fails; no numeric-PID signal, unknown descendant or API exec fallback. Only after pidfd retained may synchronous waitpid observe/reap status. Child restores intended empty signal mask before final API exec. Broker death before G closes gate and cannot launch an unknown API. Linux pidfd_open,pidfd_send_signal and execveat(AT_EMPTY_PATH) REQUIRED in this admitted Linux runtime; ENOSYS/unsupported => static unsupported, NO numeric-PID signal/exec fallback. Existing Docker Desktop uses Linux kernel but support is UNVERIFIED until actual component test. This is not a host/macOS syscall requirement.

Child remains same PID across fixed setup then FINAL FD-bound exec. Set session/group (SID=PGID=child PID), clear supplementary groups, set real/effective/saved GID/UID1800, close ALL FDs except stdio/executable/error-write, build bounded fixed env/argv. Error-write stays CLOEXEC through every setup step, VERIFIED immediately before FINAL exec; no env/setsid/setpriv wrapper may close it early. No untrusted Python/module executes as root in this sequence. Exec FD deliberately names the opened root-protected ELF, never re-resolves an API-owned PATH/symlink. Validate pyvenv behavior in actual new image, do not infer from source alone.

On any setup/exec failure child writes at most ONE16byte atomic frame `b"VAPIERR1" + uint32be(stage) + uint32be(errno)` then `_exit(70)`. stage enum1=fds,2=session,3=identity,4=exec; errno integer1..4095. Partial/extra/malformed bytes deny. Success emits NOTHING: only kernel closes CLOEXEC FD at final successful exec. Broker timeout10s covers channel and identity handshake.
