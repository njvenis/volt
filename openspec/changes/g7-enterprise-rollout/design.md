# G7 deployment and operations design

## Boundaries

VOLT and DefectDojo CE remain separate applications with separate database roles. VOLT communicates with DefectDojo through supported APIs. State-changing decisions commit with their audit events and recoverable outbound intent. No release, production deployment or writer cutover follows solely from local implementation or fixture tests.

The deployment target contains the VOLT API, UI and workers, pinned DefectDojo CE processes, separate UVM and CE databases, and the required broker in one supervised container. A local OIDC provider is a test fixture; provider compatibility must be checked against the selected identity service before release. Access groups govern authorization; ownership teams represent accountability and do not grant access.

## Data and operational controls

Ingestion timestamps are distinct from scanner observation and collection times. New SLA versions use authoritative VOLT ingestion commits and preserve prior issued reports. Approved exceptions accept risk, capture remaining SLA time and resume at expiry without erasing earlier breaches.

Audit history has a read-only, permission-scoped application view and an independently controlled SIEM copy. Export receipts, retries and reconciliation expose missing or changed records. Detection data and operational logs have distinct preservation periods; no deletion policy is inferred while retention semantics remain unsettled.

Infrastructure operates backups. Restore procedures coordinate VOLT data, DefectDojo state/media and queued external effects. External failure observation must remain available when the application container is unavailable. Writer cutover fences the outgoing writer and reconciles uncertain operations before enabling a replacement.

## Draft G7-SLA-CTX-01 identity context for policy selection

Status: proposed contract for review only. Implementation, migration and runtime changes remain paused until the primary accepts this contract.

`RuleV1` gains optional keyword-only `workload_context_fields: tuple[str, ...] = ()`. The value must be an actual tuple; each name must be an actual non-empty, already-trimmed string, unique and disjoint by exact equality from `workload_match_fields`, and must not name an ephemeral locator/host field. Preserve tuple order and reject rather than normalize, sort or deduplicate. The tuple is immutable within a `(rule_id, rule_version)` definition. Match fields alone are used for candidate discovery, workload selection/creation, and rebuild continuity. Context fields are never correspondence evidence; shared environment values cannot merge, disambiguate or select workloads. Context alone cannot create a workload. Existing match-field ambiguity remains unresolved.

When the actual retained-observation identity writer creates a new workload from match evidence, it stores only supplied non-empty context values in `stable_attrs`; the retained resolution and request fingerprint identify the exact context-bearing rule and supplied source values. Values must be actual non-empty strings; whitespace-only values are invalid and accepted values are preserved byte-for-byte without trimming or case folding. Context is usable by server-side SLA policy selection only when the writer retained it. Resolve candidates using match fields first; if ambiguous, context cannot choose a candidate. After a unique match, a supplied value that disagrees with already retained context yields unresolved evidence without persisting staged group/CVE/workload/incarnation/exposure/occurrence graph changes or any new SLA state. The source observation/retention receipt remains because source retention is a separate transaction. Preserve all existing correction and invalidation authority guards.

The context/readback matrix is explicit: (a) known stored context plus an omitted follow-up input retains the stored selector and remains usable for applicable SLA selection; omission does not weaken coverage; (b) conflicting supplied context makes that observation unresolved, creates no new coverage, and does not erase or reset an already admitted membership clock; (c) missing stored context remains unavailable even if later observations supply it—there is no enrichment/backfill; (d) a missing value is an SLA gap only when a required selector for a prospective G7 episode cannot be read from retained authoritative context; an absent unused optional context field does not blanket-create a gap. An already G5-pinned episode, including later membership in that same episode, intentionally remains G5 after policy activation. No browser-derived context or coverage is allowed.

`identity_rule_definitions` receives a non-null JSON/JSONB `workload_context_fields` column with `[]` default in migration `0062`. Before constructing `RuleV1` from stored data, require an actual JSON array/list of unique valid strings disjoint from stored match names; reject malformed values rather than coercing, sorting, deduplicating or repairing them. Provision, resolve, `matches`, restoration and scalar-correction reconstruction use the same strict representation; context fields are never scalar-correction targets. The current digest preimage is `{"fields": MATCH_FIELDS, "verified_asset_locator": VERIFIED}`; for non-empty context append exactly `"workload_context_fields": [ORDERED_CONTEXT_NAMES]`, while empty context omits the key. Downgrade is refused when any retained rule has non-empty context. Identity resolution and the coupled G7 episode/receipt/evaluation remain one transaction; separate source retention remains committed.

## G7-REC-01 current-image schema transition

The current-main Docker journey is version-specific: candidate B is the image built from the exact tested source snapshot and its complete image/package digests are retained. Its existing normal startup accepts only its declared schema head, `0061`; a candidate implementing the draft context contract would declare `0062` and accept only that exact head in normal mode. A separately labelled historical fixture continues to prove the previously accepted `0058` to `0059` transition; that fixture is not evidence for current-main compatibility. Existing `0058→0061` evidence remains bound to its captured source and is not relabelled as `0062` evidence.

For the current-image journey, the host controller journals a compatibility admission bound to the source image A, target candidate B, both package manifests, signed archive, epoch 1 and fresh forward volume IDs. The admission names exactly `0058` to `0061`; it does not authorize arbitrary migration destinations. Candidate B may enter verification-only, control-only recovery on the admitted archive head `0058`. In that mode only the recovery-control listener is available: product APIs, CE, workers and outbound product effects remain stopped until the host records the restored transition. After the explicit migration completes, only head `0061` may pass the current candidate's released runtime checks. Intermediate `0059` and `0060` heads are accepted only while the same admission and control-only migration context is active. Normal mode rejects every head except the image's exact declared head. Unknown, multiple, unadmitted or mismatched heads fail before initialization or effects.

The existing authorized migration chain is pinned to the repository revisions and their exact effects. A future candidate for the draft context contract would add `0062` only as a separately reviewed delta:

| Revision | Exact schema effect |
| --- | --- |
| `0059` | Create empty `g7_backup_projection_evidence` with primary key `deployment_id` and nullable `application_evidence_record_id` and `effective_evidence_record_id` columns. |
| `0060` | Create empty `collection_request_reservations` with its declared primary key, foreign key to `collection_runs`, unique `(run_id, attempt_no)`, and the `attempt_no`, `page_ordinal`, and digest-length checks. |
| `0061` | Add nullable `ingestion_evidence.byte_size` and check it is null or between 0 and 16777216; pre-existing records remain null and unchanged. |
| `0062` (draft only) | Add non-null JSON/JSONB `identity_rule_definitions.workload_context_fields` with default `[]`; existing definitions receive only the empty column value, and their identity, immutable digest, authorization and timestamps remain unchanged. |

The existing `0058→0061` expected inventory is computed from its captured `0058` source inventory, exact migration definitions, and retained host-journal receipts. It permits only the three named schema effects, the `alembic_version` transition, empty new-table contents, and exact journal-derived recovery-control row/field deltas. A future `0058→0062` inventory must independently add exactly the `0062` column and its default-empty values to the existing rule rows; it cannot edit or reuse the previous `0058→0061` expectation. A narrow `0061→0062` proof starts from its own captured `0061` inventory. No route permits migration-created product rows, changes to other existing product payloads/digests, desired-revision changes, CE table or media changes beyond journaled recovery controls, or changes inferred from candidate observations alone. Any unrecognized table, column, constraint, schema head, row, payload, or control-field delta rejects rollback.

Forward migration runs on fresh epoch-1 volumes. PostgreSQL DDL and the Alembic version update execute in the migration transaction; an injected failure at each revision boundary must leave the database at the original `0058` inventory or at a fully committed known head, never an accepted partial schema. Recovery does not downgrade this database. It keeps ingress and egress fenced, verifies zero post-backup product writes and no unresolved external effects, then restores the original signed archive with its bound source image A onto a separate fresh volume set at a strictly higher external recovery epoch. The rollback attestation compares complete UVM and CE table/schema/row-payload inventories and CE media digests, and epoch-2 readback is signed over the restored A image/package, archive, new volume IDs, connector context and current CE/UVM/media state. The retained post-backup controls are replayed from the host journal; they are not fabricated in the archive or treated as migration output.

The migration and rollback proof must demonstrate that recovery-control startup against schema `0058` does not query tables introduced by `0059`/`0060` or columns introduced by `0061`/`0062` before migration. Product and CE readers start only after migration and the signed restored-state gate. For a `0062` candidate, inject failure at the new revision boundary and prove the database remains at the original admitted head or a fully committed known head. If exact inventory, isolation or transactional failure behavior cannot be established, the current-image journey remains unverified and its dependent activation stays paused.

## Versioned operational settings

The first setting slice is deployment-scoped observer timing. A VOLT command stores the desired revision, audit record, receipt and application intent atomically. A separately controlled host service validates and applies the revision, then reports the effective state. The UI distinguishes pending, applied, failed and uncertain states and shows last-known effective configuration during VOLT outages. A rollback creates a new revision. Host policy and controller credentials remain outside VOLT.

See `docs/g7-observer-settings-contract.md` for the request and readback contract. Local timing values are fixtures, not release policy.
